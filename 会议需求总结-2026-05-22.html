核心痛点 1. 采购单录入 — 减少重复输入

痛点：当前每次采购都需要手工逐条输入供应商、产品名称、数量等信息，效率低且容易出错。大多数采购是从同一供应商重复采购相同的产品，仅数量有变化。

客户期望的解决方案

  • 供应商单据导入：供应商通常会提供 PDF 或 Excel 格式的送货单/发票。客户希望直接上传该文件，系统自动识别并生成采购单草稿，人工检查确认即可。
  • "再来一单" 功能：基于历史采购单快速复制，保留供应商和产品列表，仅修改数量即可。
已达成共识：优先实现"上传 PDF/Excel → 自动生成采购单"功能。同时支持从历史订单快速复制。

功能需求 2. 采购单工作流与库存联动

工作流程

创建草稿 (Draft) → 等待供应商送货 → 核对/修改数量与产品 → 确认 (Confirm) → 库存自动更新 (Forecast + On Hand)
  • 采购单创建后为草稿状态，供应商送货到仓后进行核对
  • 如果数量或产品有变更，在草稿阶段直接修改
  • 确认 (Confirm) 后，系统自动更新 Forecast 和 On Hand 库存
  • 确认后的采购单不可再编辑，如需修改只能走退货 (Return) 或报废 (Scrap)
业务规则：分两个阶段 — Confirm 前可自由编辑；Validate（实际入库）后数据锁定，只能做 Return 或 Scrap。

核心痛点 3. 客户订单处理 — 库存预警与锁定

痛点：多个销售人员同时下单时，无法实时看到库存已被其他订单锁定。导致仓库拣货时频繁发现缺货，需要反复改单。

需求

  • 实时库存锁定：销售录入订单时，被其他订单锁定的库存应即时扣减显示。例如 On Hand 1107，其他销售已锁定 1105，则当前销售仅能看到剩余 2。
  • 醒目的库存预警弹窗：当产品库存低于安全阈值时，在订单录入界面以弹窗或醒目标识提醒（当前系统有此功能但不够明显）。

核心痛点 4. 订单改单流程优化

痛点：Odoo 中已确认的 Quotation 不允许直接删除产品行或修改数量（仅能改价格）。当前流程：Cancel 整个 Quotation → 重新创建 → 重新录入。产生大量冗余订单和 Delivery Slip，容易搞混。

期望行为

  • 在出库 (Validate) 之前，订单应允许直接编辑：修改数量、删除产品行、新增产品行
  • 编辑时系统自动调整虚拟库存（释放被删除产品的锁定库存，锁定新增产品的库存）
  • 无需 Cancel → 重建的繁琐流程
  • 出库 (Validate) 后订单锁定，修改只能通过退货 (Return) 或报废 (Scrap)
已达成共识：新系统直接支持编辑已确认但未出库的订单，自动处理库存增减。避免产生冗余订单。

优化需求 6. 库存出库批量处理 (Inventory Validate)

痛点：当天 148 个订单需要做出库操作 (Inventory Validate)，当前系统只能每次处理 20 个，每次等待 2-3 分钟。通常要等到凌晨 3 点司机出发后才能开始处理。

需求

  • 批量处理数量从 20 提升到 50（最多 100，考虑数据库性能）
  • 处理过程中偶尔出现莫名失败（非库存冲突原因），需要有操作日志便于排查
  • 系统需防止重复操作（如用户以为处理完了但后台还在执行）
已达成共识：批量上限提高到 50-100，需有明确的进度反馈和完成状态提示。超过 100 不建议（等待时间过长且易出错）。

核心痛点 7. 退货处理优化

当前流程 (Odoo)

找到原始 Sales Order → 进入 Delivery → 点 Return → 选择退货产品和数量 → 确认退货 → 库存恢复
痛点 1 — 多单合并：同一客户退回的商品可能来自 3 个不同的原始订单。当前需要分别在 3 个原单上做 Return，生成 3 张 Credit Note。客户希望收到 1 张合并的 Credit Note。
痛点 2 — 日期错误：做 Return/Credit Note 时，系统自动使用原始订单的日期。但如果原单是 2-3 个月前的，Credit Note 的日期也变成旧日期，导致上传 Sage 时账期错误、单据"丢失"。

期望行为

  • 退货/Credit Note 的日期默认使用当天日期（即实际处理退货的日期），而非原始订单日期
  • 支持跨订单合并退货：同一客户从多个原始订单退回的商品，可以合并生成 1 张 Credit Note
  • 退货后库存自动恢复

功能需求 8. 财务对账与 Sage 导出

当前流程

Sales Order 确认 → 出库 (Validate) → 回单确认（纸质单据回收） → 生成 Draft Invoice → 确认 Invoice → 导出表格上传 Sage

需求

  • 需要了解 Sage 要求的导出格式（待客户提供模板）
  • 导出的日期字段需要正确（参见退货日期问题）
  • 周结或月结汇总导出
待办：客户将提供 Sage 上传的 Excel 模板，据此设计导出格式。

功能需求 9. 库存移动全链路追踪

需要追踪的库存变动类型

类型说明对库存的影响
采购入库供应商送货 → 确认入库On Hand +
销售出库订单确认 → 拣货 → 出库On Hand −
退货入库客户退货回仓On Hand +
报废 (Scrap)损坏/过期产品报废On Hand −
手动调节人工盘点差异调整On Hand ±
  • 所有类型的库存变动都必须在 Inventory Movement 记录中可查
  • 每条记录关联到源单据（采购单号/销售单号/退货单号等）
  • 手动调节与系统自动变动需明确区分
  • 采购记录需关联供应商和采购价格
关键需求：手动调节的路径可以不对所有人开放，但系统必须保留此功能入口，并有完整的操作日志。

功能需求 10. 批次号 (Lot/Batch) 与保质期管理

  • 批次号来源：扫描枪扫描（优先）或系统自动生成
  • 保质期 (BBD / End of Life)：每个批次需记录保质期截止日期
  • 到期预警：临近保质期的产品需要在系统内直接提醒（优先于邮件通知），希望在界面上直观显示
  • 后续考虑对接扫描枪硬件（当前阶段暂不实现）

已知缺陷 11. 大小单位与小数退货问题

痛点：产品存在大小单位关系（如 虾饺 1箱 = 5×2.5kg）。退货非整数时（如退 0.3333 箱），Odoo 的退货逻辑会将整个 Delivery 的数量清零，而非精确扣减。当前只能通过直接修改数据库解决，操作不规范。

期望

  • 退货支持小数精度，正确处理部分退货
  • 退货后 Delivery 数量应精确扣减（不是清零）
  • 系统提供合规的修正路径（而非直接改数据库），该路径可限制权限但必须存在

功能需求 12. 采购预定日期与库存批次

  • 采购单创建日期与实际到货日期 (Scheduled Date) 可能不同（如今天下单，下月到货）
  • 到货入库时，库存批次的日期应跟随 Scheduled Date，而非采购单创建日期
  • 系统需正确维护 Scheduled Date 字段，并在入库时使用该日期记录批次

需求优先级总结

P1 — 重要批量出库提升到 50-100 单减少凌晨加班时间
P1 — 重要库存移动全链路追踪业务透明度
P1 — 重要小数退货精确处理消除数据库手动修改
