# 配送调度台新增「分配完成」状态 — 设计文档

- 日期：2026-07-03
- 范围：配送调度中心（`dispatch-console` / BatchTab）批次卡片状态机
- 类型：中等改动（1 schema 字段 + 1 迁移 + 1 新 API 路由 + 改 2 路由 + 改 1 组件）

## 1. 背景与目标

配送调度台每个司机批次卡片当前有三个阶段：

1. **未出发**：可拖拽调整订单，底部「🚚 确认出发」。
2. **在途**（`dispatchedAt` 已标记，锁定不可拖）：底部「✓ 标记完成」。
3. **已完成**（`completedAt` 已标记）：卡片从调度台归档。

「确认出发」是有真实下游副作用的闸门：回填订单 `deliveryDate=排程日` 并转 `IN_DELIVERY`，订单由此才出现在**日销售管理中心**、可打印拣货单等（打印取数条件为 `status=CONFIRMED,WAVE_ASSIGNED,IN_DELIVERY` ＋ `dateField=deliveryDate` 按当天筛选，见 `PrintCenter.tsx:305`）。

目标：在「确认出发」之前插入一个 **「分配完成」** 状态，作为调度员的**纯进度标记**，帮助一眼看出哪些批次已排好；但在点「确认出发」之前，批次仍可自由修改。

## 2. 需求确认（已与用户敲定）

- **语义**：纯进度标记，可反悔。不触发任何后端动作（不通知司机、不生成拣货单、不推进 `WaveStatus`、不碰 `status`/`deliveryDate`）。
- **不强制**：不是确认出发的前置条件。「分配中」和「分配完成」都能直接点「确认出发」。
- **修改行为**：批次处于「分配完成」时仍可直接拖拽订单；一旦有增/删/移，`assignmentDoneAt` **自动清空**，退回「分配中」，需重新点「分配完成」。
- **手动撤销**：另给「↩︎ 撤销」按钮，用于误点后不改分配也能退回。
- **顶部看板**：新增「已排完 N」计数。

## 3. 状态模型

每个司机批次卡片按以下优先级判定（前端 `Lane`）：

| 顺序 | 判定字段 | 状态 | 可否拖拽 | 卡片底部按钮 |
|---|---|---|---|---|
| 1 | `completedAt` | 已完成（归档） | — | 卡片移出调度台（不变） |
| 2 | `dispatchedAt` | 🚚 在途 | ❌ 锁定 | ✓ 标记完成（不变） |
| 3 | **`assignmentDoneAt`（新增）** | **✅ 分配完成** | ✅ 可拖 | 🚚 确认出发 ＋ ↩︎ 撤销 |
| 4 | 都为空 | 分配中 | ✅ 可拖 | ✅ 分配完成 ＋ 🚚 确认出发 |

优先级说明：`completedAt` > `dispatchedAt` > `assignmentDoneAt` > 分配中。即出发后 `assignmentDoneAt` 即便有值也不再影响展示（以 `dispatchedAt` 为准）。

## 4. 数据模型

`PickingWave` 增加一个字段，与现有 `dispatchedAt` / `completedAt` 同风格：

```prisma
/// 分配完成标记时间：调度员点「分配完成」后回填，纯进度标记，可反悔；订单一变动即清空
assignmentDoneAt DateTime?
```

迁移策略遵循项目既有教训（Prisma migrate dev 因旧迁移在 shadow DB 重放失败）：用 `prisma db push` 应用到本地库 + 手写迁移文件 + `prisma migrate resolve --applied` 登记，**不使用 `migrate dev`**。字段为可空、无默认约束外的副作用，对存量数据安全（存量波次 `assignmentDoneAt=NULL`，即「分配中」，与现状一致）。

## 5. 后端 API

### 5.1 新增 `PUT /api/waves/[id]/assignment-done`

请求体：`{ done: boolean }`

- `done: true`：设 `assignmentDoneAt = new Date()`。
  - 校验：批次存在；`orderIds.length > 0`（空批次不能标记分配完成）；未 `dispatchedAt`（已出发不允许）。
- `done: false`：设 `assignmentDoneAt = null`（撤销）。
- 鉴权：复用 `withAuth`（与同目录其余路由一致）。
- 返回：`serializeApi(updated)`。
- 写 `action-log`：`分配完成 / 撤销分配完成：批次 X`。

### 5.2 改 `assign` / `unassign` 路由

两个路由在 `prisma.pickingWave.update` 的 `data` 中追加 `assignmentDoneAt: null`——订单一变动即自动退回「分配中」。`moveWave` 前端走的正是 `unassign` + `assign` 两次调用，天然覆盖「换车」场景。

### 5.3 `dispatch` / `complete` 路由

**不改**。确认出发不要求先分配完成；出发/完成流程与 Trip 生成逻辑均不受影响。

## 6. 前端 `BatchTab.tsx`

- `Wave` 接口加 `assignmentDoneAt: string | null`。`serializeApi` 已整体序列化波次，list API 无需改。
- 新增 `markAssignmentDone(waveId, done)`：调用 5.1，乐观更新对应 wave 的 `assignmentDoneAt`。
- `assignToWave` / `unassignFromWave` / `moveWave` 的乐观更新里，把涉及批次的 `assignmentDoneAt` 一并置 `null`（与后端一致，避免闪烁）。
- `Lane` 增加「分配完成」渲染分支：
  - 展开态：徽章「✅ 分配完成」；底部按钮「🚚 确认出发（N单）」＋「↩︎ 撤销」。
  - 折叠态：徽章同步显示「✅ 分配完成」。
  - 仍 `draggable`（区别于在途的锁定）。
- 「分配中」展开态底部：订单数 > 0 时，在「确认出发」旁/上方新增「✅ 分配完成」按钮。
- 顶部看板新增 `Board`：「已排完」= `waves.filter(w => w.assignmentDoneAt && !w.dispatchedAt).length`。

## 7. 影响面与非目标

- **影响**：`schema.prisma`（+1 字段）、1 个新迁移、`assign`/`unassign` 路由各 +1 行、新增 `assignment-done` 路由、`BatchTab.tsx`。
- **非目标**：不改打印/日销售中心取数逻辑（天然兼容）；不改 dispatch/complete/Trip 生成；不改 `WaveStatus`（理货进度）语义；不做「分配完成」触发的任何自动化。

## 8. 验证要点

1. 空批次不显示「分配完成」按钮；点击被后端拒绝（若绕过前端）。
2. 标记分配完成 → 徽章出现、看板「已排完」+1、订单**未**进日销售中心打印列表。
3. 分配完成后拖入/拖出/换车订单 → 徽章消失、退回「分配中」、看板「已排完」-1。
4. 分配完成后点「↩︎ 撤销」→ 退回「分配中」，分配不变。
5. 分配完成（或分配中）直接点「确认出发」→ 正常转在途、回填 `deliveryDate`、订单进日销售中心可打印。
6. 已出发批次不受影响：不显示分配完成分支，仍为「在途 → 标记完成」。
7. 存量波次加载后默认「分配中」，无异常。
