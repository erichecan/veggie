# 需求原话：采购运费分摊成本联动

日期：2026-10-17

## 来源

客户在采购单详情页（PO-00140，供应商 Mitro fresh）截图上用红框手写批注，用户（eric）通过微信转发原图，并要求"先识别一下客户的需求,然后仔细分析一下需求"。以下批注文字为截图逐字抄录（客户原话，非用户转述）。

## 客户原话（截图批注，逐字抄录）

左侧两条：

> 之前订单所产生的 cost

> 这个订单所产生的新的cost，这个cost与供货商，PO 号，订单确认日期，数量是连在一起的。

右侧编号 ①-⑤：

> 1. 对于storable 或 consumable产品，总的费用除以总箱数 得出每箱的 分摊费用。
> 2. 根据实际需要 每个产品分摊的费用 调整，+或-
> 3. 每个产品 分摊费用合计 与 总费用 要对的上
> 4. 订单确认，新形成的cost,作用到 public price
> 5. 如订单取消，这次形成的cost也取消。恢复到之前的。

## 用户原话（20261017，对①-⑤的再次复述，澄清分摊基数）

> "1,基础单位的分摊费用;2 每个分摊费用需要可以手动调节,3,每个分摊费用最终的总费用要对得上 4,订单确认,新的 cost 应用到 public price;5,如果取消了订单,那这次的成本计算也取消了,恢复原来的成本"

第 1 点把最初截图的"总箱数"换成了"基础单位"，经 `AskUserQuestion` 当面确认两点（均选推荐项 A）：

1. 同一采购单里各行下单单位不统一（如部分 CASE、部分 KG）时，分摊基数**先按各商品自己的换算系数折算成基础单位，再按比例分**，不直接用下单数量的裸数字比。
2. 像 "Transport PALLET" 这类物流/非产品行（无真实单位），**排除在分摊基数之外**，与 SERVICE 类行同等对待——核实后发现后端一直就是这么做的（`Transport PALLET` 的 `Product.type` 本身就是 `SERVICE`），前端此前显示异常是另一个已修复的 bug（ⓘ 参考成本列查看态不加载数据）的连带症状，不是这条本身有问题。

## 用户原话（20261017 第二轮，同一张截图上的新一批红框批注）

用户转发同一张采购单编辑页截图，图上另有红框标注。用户先描述图上标注，随后给出以下逐条澄清（用户原话，逐字抄录，未转述）：

> 1,首先 product 要包含 spec 和 description
> 2,创建的采购单保存后就计算了 cost,并且再进入编辑的模式下,可以手动调节
> 3,增加一列是 per case freight 的成本,这里是可以手动调节的,默认是 freight 除以箱数,per case freight 乘以箱数,算出 alloc.freight
> 4,在 alloc.freight 最下面增加 total,在 qty 最下面也增加 total
> 5,untaxed total 去掉
> 6,subtotal 在最下面的是 subtotal 的加总

### 实现对应与结论（本次改动）

- 第 1 点：核实为已实现（`GET` 路由早已把 `productSpec`+`description` 合并到 `spec` 字段），截图里的空白是历史行本身没填数据，不是代码缺陷，未改代码。
- 第 2 点：此前只有「确认采购」才写 `landedUnitCostEur`，草稿/已发送阶段保存不算。本次给 `PUT` 加了保存即重算逻辑（仅 `DRAFT`/`SENT`，不碰 `Product.standardPrice`，那个联动仍然只在确认时发生）。验证时发现并修复一个连带 bug：保存接口返回体用的是重算前的行数据，保存后前端拿到的还是旧值，要刷新页面才看到——已改成重算后立即回填进响应体。
- 第 3 点："Per Case Freight" 复用既有的 `allocatedFreightEur` 覆盖字段做反推显示/反算回写，没加新字段：编辑这一列时按 `当前数量 × 输入值` 换算回 `allocatedFreightEur` 存库，与"确认采购"用的分摊算法共享同一套 null=自动/数字=手动 语义。
- 第 4/6 点：给共享表格组件 `OrderLineEditor` 加了 `footerRow`（跟数据行同一张 `<table>` 里的合计行，列对齐），页面里接入 Qty、Alloc. Freight、Subtotal 三栏合计。
- 第 5 点：移除 Untaxed Total 列。

## 用户原话（20261017 第三轮，针对采购询价单打印模板的截图批注）

用户转发采购询价单（REQUEST FOR QUOTATION，PO-00144，供应商 Mitro fresh）打印模板截图，图上 DESCRIPTION 列右侧空白处有红框批注 "product spec description"。用户原话：

> 这个采购询价单的打印模板中,也给 product 加上 spec 和 description 的描述

### 实现对应与结论

`lib/purchase-order-pdf.ts`（RFQ/采购单打印模板，三个调用点：单张打印、邮件附件、批量打印共用同一渲染函数）的 DESCRIPTION 列原来只显示商品名，没有 spec/description。改为在商品名下方补一行（红色小字），内容为 `[productSpec, description]` 过滤空值后用 `·` 拼接，与编辑页/GET 路由的合并口径一致，并沿用 `lib/order-pdf.ts`（销售单打印模板）已有的 `.prod-name`/`.prod-spec` 样式先例。用真实数据（含有 spec+description 都有、只有 description、都为空三种情况）跑了 PDF 渲染接口验证，三种情况都正常，无残留空白标签。
