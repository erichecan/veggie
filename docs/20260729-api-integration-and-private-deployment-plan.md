## 1. 改造方案 A：标准对外 API 层

（本节与第一版一致，客户新条款未涉及此部分，方案不变，仅保留摘要，完整设计见文末附录或上一版本历史。）

- 新建独立命名空间 `/api/external/v1/*`，与现有 151 个内部 API 彻底分离，API Key + HMAC 签名鉴权，`scopes` 粗粒度授权
- 分域对接：ERP（商品/库存/订单双向）、财务系统（发票/总账凭证导出）、电子秤（需独立边缘网关，非 HTTP 协议）、税控盘（需先确认目标市场合规路径）、物流平台（运单双向 + webhook）
- Webhook 出站机制 + OpenAPI 自动生成文档 + 限流审计

> 注：这部分工作量和优先级评估维持第一版结论（P1-P3，见第 8 节路线图），本次更新的重点在下面第 2-6 节。

## 2. 改造方案 B：私有化部署（部署在客户服务器，与 Odoo 12 独立并行）

这是本次更新的核心，**合同条款已明确写死，不是可选项**。逐条对照当前系统能力：

### 2.1 部署责任划分（合同已定义，仅作技术侧确认）
- 甲方（客户）：提供服务器，承担购买/租赁/续费及第三方基础费用
- 乙方（我方）：新系统安装部署、开源数据库安装配置初始化、数据库结构设计/权限/备份恢复方案、Odoo 12 安装配置运行环境、两系统的地址/端口/数据库/目录规划、服务器运行环境与安全设置

**技术侧结论**：这要求我方交付的不是"一个能跑的 Docker 镜像"，而是一整套**服务器初始化 + 双系统安装 + 运维交接手册**，比现在"push 到 GitHub 自动部署到 Cloud Run"的心智模型重得多。

### 2.2 数据库层解耦（私有化的第一道硬门槛）
- 现状：`lib/db.ts` 写死 `PrismaNeon` adapter，走 WebSocket 协议连 Neon 云服务，客户自己服务器上装的普通 PostgreSQL **无法直接连**
- 改造：按环境变量切换 `DATABASE_DRIVER=neon | pg`，私有化场景用标准 `@prisma/adapter-pg` + `pg` 连接池连本地/局域网 PostgreSQL。Prisma schema 不用改，只改 `lib/db.ts` 一处初始化逻辑
- 工作量：小-中

### 2.3 存储层抽象
- 现状：`upload-image`、`pdf-extract` 硬编码 `@google-cloud/storage`，客户服务器没有 GCS
- 改造：抽 `lib/storage.ts` 的 `StorageProvider` 接口，私有化默认落到服务器本地磁盘目录（对应合同里的"独立文件存储目录"要求），可选加 MinIO/S3 兼容支持
- 工作量：中

### 2.4 双系统独立并行运行——逐条对照合同要求

| 合同要求 | 技术方案 |
|---|---|
| 程序运行环境相互独立 | 新系统用 Docker 容器运行（已有 Dockerfile，验证过不依赖 GCP 专有能力），Odoo 12 用其官方推荐的独立 Python venv 或另一个容器，两者物理隔离，互不共享进程/依赖 |
| 数据库相互独立 | 新系统一个独立 PostgreSQL 实例/库，Odoo 12 保持其原有的 PostgreSQL 实例/库（Odoo 12 官方也是 PG），**两个完全分开的数据库进程或至少分开的 database + 独立账号**，不共用连接池 |
| 文件存储目录相互独立 | 各自固定路径（如 `/data/veggie/uploads` vs `/opt/odoo/filestore`），权限隔离，避免误覆盖 |
| 系统账号及权限相互独立 | Linux 系统用户级隔离（如 `veggie` 用户跑新系统容器，`odoo` 用户跑 Odoo），数据库账号也分开，任何一套系统故障不会带崩另一套的进程 |
| 访问地址/端口相互独立 | 新系统与 Odoo 12 各自绑定不同端口，建议前面统一挂一个 Nginx/Caddy 反向代理做域名/子域名分流（如 `new.客户域名` / `odoo.客户域名`），两个后端服务互不感知 |
| 日志及备份机制相互独立 | 见 2.5 |
| 任一系统升级/重启/故障不得未经授权影响另一套 | 通过上面的容器/进程/账号隔离自然满足，另外建议 Nginx 层配置健康检查+独立限流，避免一套系统流量异常拖垮另一套所在的宿主机资源（需要评估服务器规格是否够跑两套系统，见第 9 节问题清单） |

**工作量**：中-大（不是纯代码改造，涉及服务器规划、Nginx 配置、进程管理配置 systemd/docker-compose，属于运维交付工作，需要专门写一份《服务器部署与隔离操作手册》）

### 2.5 备份与恢复方案（当前系统层面完全空白，必须新建）

合同要求：数据库定期自动备份、程序文件和上传文件定期备份、至少一份保存在异地、备份可恢复、客户能拿到完整备份文件——这四条现在项目里**一条都没有**（现有的 `backups/` 目录只是数据迁移时的一次性手工快照）。

新建方案：
- **数据库备份**：`pg_dump` 定时任务（cron，每日全量 + 可选 WAL 归档做时间点恢复），新系统和 Odoo 12 各自独立的备份任务、独立的备份文件目录
- **文件备份**：`rsync`/`tar` 定时打包上传文件目录，同样两套系统分开
- **异地存储**：备份产物定时同步到一个不同于主服务器的位置（可以是客户自己的另一台机器、或客户认可的云对象存储，需和客户确认接受哪种）
- **可恢复性验证**：不能只是"生成了备份文件"就算完成，需要定期（建议每季度）做一次实际恢复演练并出报告，这是合同"备份可正常恢复"这句话真正要求的东西，很多项目会漏掉这一步
- **交接**：备份文件访问方式、恢复操作手册要交给甲方，甲方能自主取得完整备份

**工作量**：中（技术不难，是"从零到有"的量，加上要写操作手册和做恢复演练）

### 2.6 管理员账号与技术资料交接（流程约定，非代码工作）
合同要求服务器、数据库、新系统、Odoo 12 的最高管理员账号密码、数据库访问权限、备份文件、技术资料都归甲方掌握，乙方不得限制甲方访问/导出/备份/接管。技术上需要：
- 部署时用甲方自己创建/掌握的账号体系，而不是乙方自建后"共享"给甲方
- 提供一份完整的《系统交接清单》：所有账号密码、数据库连接串、备份路径、部署脚本、源代码仓库访问权限，逐项确认甲方已拿到并能自主操作
- 这条主要是流程和文档工作，技术上不难，但容易在实施中被遗漏，建议列入验收清单

### 2.7 多租户架构（本合同不涉及，但要澄清概念，避免和"双系统"混淆）
上一版文档里讨论的"多租户共享实例"方案（一套代码服务多个 SaaS 客户），**与本次的"双系统独立并行"是两回事**：
- 本合同要的是"同一个客户"的新旧两套系统在同一台服务器上并行——这是**部署隔离**问题，用 2.2-2.6 的方案解决，不涉及多租户数据模型
- 之前讨论的"多租户"是"多个不同客户共享一套 SaaS 部署"——如果以后有其他客户想用 SaaS 云端版本，才需要考虑这个，与当前合同无关，暂不需要投入

## 3. 改造方案 C：灵活数据分析（Odoo 式多维度可组合分析）

现状是"预设报表"，离合同要求的"多条件筛选、多维度分组、多种统计指标、可组合"有明显差距，需要新建一套通用透视引擎，而不是在现有 7 个分析页面上小修小补。

方案方向：
- **后端**：设计一个通用的 `/api/analytics/pivot` 接口，接收 `dimensions[]`（可多选：客户/产品/品类/销售员/司机/月份/周…）+ `measures[]`（可多选：销售额/毛利/毛利率/数量/订单数…）+ `filters`（多条件组合，而不是现在只有日期范围），后端按传入的维度组合动态 `GROUP BY`，而不是像现在 `GROUP_DEFS` 那样为每种分组写死一条 SQL
- **前端**：类似 Excel 数据透视表的交互组件（拖拽字段到"行/列/值"区域，或至少是多选下拉的组合筛选面板），销售分析和采购分析两个场景共用同一套透视组件，只是可选维度/指标的字典不同
- 现有 7 个预设分析页面可以保留作为"常用视图快捷入口"，透视引擎作为补充，不是推倒重来

**工作量**：大（后端动态查询引擎 + 前端透视表交互组件，是一个独立的功能模块，建议单列一个开发阶段）

## 4. 改造方案 D：权限管理与角色矩阵

现有 `Role` 是粗粒度大类，`User.roles` 已支持一人多角色（数据结构具备），但缺两块：**功能级操作权限**和**复合角色的业务逻辑**。

合同要求的角色矩阵：

| 角色 | 权限范围 |
|---|---|
| 客户（网站/APP下单） | 仅下单，现有 `customer` 端已支持 |
| 外聘销售员 | 录入订单 |
| 办公室销售员 | 录入订单 + 录入购进单 |
| 高级销售员 | 销售 + 直接负责采购 |
| 销售经理 | 销售 + 采购 + 司机（三域复合） |
| 仓库经理 | 卸货、质检、配货、出库、库存管理 |
| （特定）办公室销售 | 仅这部分人能操作"配送中心""打印中心" |

改造方向：
- **不建议**再加更多 `Role` 枚举值去覆盖每一种组合（会导致角色爆炸、未来加一种组合又要加枚举）。推荐做法：保留粗粒度 `Role`/`roles[]` 作为"身份大类"，在此之上新增一张**功能权限表**（如 `Permission` / `UserPermission`），按"功能点"（下单/审核订单/录入采购单/操作配送中心/操作打印中心/管理司机…）做细粒度授权，页面和 API 从"判断 role"改造成"判断 permission"
- "配送中心""打印中心"当前是 `role === 'OPERATOR'` 就能进（`layout.tsx` 第 66 行），需要改成查具体的功能权限，而不是整个大类放行
- "销售经理管销售+采购+司机"这种复合角色，用 `roles: ['SALES', 'PURCHASE', 'DISPATCH']` 这种多角色叠加 + 对应功能权限的并集来实现，不需要新建一个专门的"销售经理"角色值

**工作量**：中-大（新增权限表 + 全站权限点梳理 + 各页面/API 的权限判断逐个改造，改动面广但单点改动不复杂）

## 5. 司机绩效管理——已基本满足，无需大改

`lib/commission.ts` 已完整实现 Product Commission（`Product.commissionPrice`）和 Customer Commission（`commissionRate`/`commissionFixed` 两种模式），接入订单和交货流程，`Trip.driverCommission` 做结算落地。这条合同要求**现状基本满足**，只需按后续实际验收反馈做细节调整，不需要新开发工作量。

## 6. 商务条款对技术方案的提示：保修期

合同提到"上线后 6 个月免费保修期（最好 9 个月），一般维护及小型修改、网络安全等与年费挂钩"——这是商务条款，不改变技术方案本身，但提示两件事：
1. 保修期内的 Bug 修复响应机制（比如是否要有工单系统/响应时限承诺）需要和商务条款一起明确，建议在交付文档里单列一节
2. "网络安全"被和年费挂钩，意味着 2.4/2.5 里的服务器安全加固、备份验证等工作，保修期后需要按年费合同持续投入，不是一次性交付完就不管——这会影响第 8 节路线图里要不要把"安全加固"做成一次性还是纳入可持续运维范围

## 8. 分阶段路线图与工作量估算（本次更新，重新排优先级）

私有化双系统部署是合同硬性条款，优先级上调到最前面：

| 阶段 | 内容 | 工作量 | 依赖 |
|---|---|---|---|
| **P0** | 数据库层解耦（2.2）+ 存储层抽象（2.3） | 小–中 | 无，立即可开始 |
| **P0** | 双系统独立并行部署方案落地（2.4）+ 服务器部署手册 | 中–大 | 依赖 P0 数据库/存储改造，且**需要先拿到客户服务器规格**（见第9节问题） |
| **P0** | 备份与恢复方案（2.5） | 中 | 依赖 P0 部署方案定型 |
| **P0** | 管理员账号与技术资料交接流程（2.6） | 小（流程为主） | 依赖部署完成 |
| P1 | 权限管理与角色矩阵改造（第4节） | 中–大 | 无，可与 P0 并行开发 |
| P1 | 对外 API 层基础设施 + ERP 对接（第1节） | 中 | 无 |
| P2 | 灵活数据分析/透视引擎（第3节） | 大 | 无，工作量大建议单列阶段 |
| P2 | 财务系统导出接口、Webhook、物流对接（第1节其余部分） | 小–中 | 依赖 P1 API 基础设施 |
| P3 | 电子秤边缘网关 | 大 | 需先拿到设备品牌/型号/协议文档 |
| P3 | 税控盘对接 | 大，方向未定 | 需先确认目标市场 |

> 相比第一版，这次最大的调整是：**私有化部署从"以后有需要再做"变成 P0 最高优先级**，因为它是合同硬性条款，而多租户 SaaS 共享实例（原方案里工作量最大的一项）在本合同场景下反而不需要做。

## 9. 实现前必须业务侧/客户侧先确认的问题

1. **客户服务器规格**：CPU/内存/磁盘，是否够同时跑新系统 + Odoo 12 两套服务？（这直接决定 2.4 能不能顺利落地，规格不够需要提前和客户沟通升配）
2. **Odoo 12 现状**：目前跑在什么系统上（是否已经是同一台目标服务器、还是要迁移）、用什么数据库版本、有没有现成的部署脚本可以复用
3. **异地备份存放位置**：客户认可"异地"是指另一台自有服务器，还是可以用云对象存储（如果客户对数据出境/上云有顾虑，两种方案实现和成本不同）
4. **保修期内响应机制**：是否需要工单系统或明确的响应时限承诺，这会影响是否要为保修期单独开发一个轻量的问题跟踪功能
5. **税控盘目标市场**：具体国家/地区，直接决定技术路线（欧洲财政收银机规范 vs 中国大陆税控盘完全是两套技术栈）
6. **电子秤设备信息**：品牌、型号、通信协议——决定边缘网关方案能否定型
7. **对外 API 第一批优先对接谁**：ERP、财务、物流三个方向工作量都不小，需要业务侧排出优先级

---

## 10. 风险提示

- **私有化部署的实际瓶颈往往不是代码，是服务器环境**：客户服务器的操作系统版本、已装软件、网络策略（能不能装 Docker、防火墙规则）如果和预期不符，会拖慢 P0 阶段，建议尽早拿到服务器访问权限做一次环境摸底。
- **备份"可恢复"是最容易被验收忽略、出了事故最致命的一环**：建议明确写进验收清单——不是"有备份文件"就算过，必须做过至少一次真实恢复演练并留存记录。
- **双系统共存对服务器资源的挤占**：Odoo 12 + 新系统 + 各自数据库同时跑在一台机器，如果服务器规格是按"只跑一套系统"配置的，上线后可能出现资源争抢导致两边都变慢，这是很容易被低估的风险，建议在第9节问题1确认后做一次容量评估。
- **权限颗粒度改造涉及全站页面/API 逐个梳理**，改动面广，建议先出一份完整的"功能点清单"评审过一遍再动代码，避免漏改导致权限漏洞。
- **对外 API 一旦发布给第三方，接口契约变更成本高**，建议 P1 阶段先找 1-2 个种子客户/ERP 服务商做联调验证，不要一次性对所有客户开放。
