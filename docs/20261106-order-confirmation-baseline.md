回滚风险：单单确认在分配失败后手动恢复状态及司机字段，恢复失败被忽略；这不能证明整个操作能回滚。批量确认先更新所有订单，后逐单处理，中途失败可能留下已成功、失败回退、尚未处理但已确认三种结果。以上均需故障验证确认实际数据结果。

## 三个衡量指标

1. 遗漏：记录固定场景清单中的不一致结果数 / 已验证场景数；另记录上线后相同根因的再次出现次数。未验证不计作通过。修复前后使用相同场景，生产反馈必须注明观察窗口和操作量。
2. 回滚：逐个关键写入点模拟失败，核对订单、确认时间、波次、托盘、库存流水、送货单和审计。分别记录完整恢复、明确的部分成功、无法解释的残留。成功标准取决于事先确定的操作契约。
3. 入口一致性：使用同一组业务输入，经三个入口得到的业务事实应一致。技术 ID、时间和批量包装响应可以不同；司机归属、单位数量、库存处理、送货单不能无解释地不同。

## 首批验收场景

- 无预安排司机：确认后保持待分配。
- 已预安排司机：确认后归属正确配送日期、司机、时段和托盘，配送中心与订单详情一致。
- 目标波次锁定、司机批次无效：失败结果明确，不能返回成功却缺失必要关联。
- 重复点击、重试、并发确认：不重复波次归属、托盘明细、送货单或库存影响。
- 批量中间一单失败：成功/失败/未处理数量与每张订单实际状态相符，不能只返回笼统失败。
- 相同商品不同销售单位：订单行数量、单位与库存换算保持一致。

## 推进顺序与停止条件

1. 确认业务契约：哪些关联必须与确认一起成功，哪些允许延后；批量操作采用整批原子或逐单明确结果，两者择一并记录。
2. 在隔离测试库建立以上场景和故障验证，记录首轮实际结果。不得对生产数据注入故障。
3. 仅对已证实的差异实施小范围调整，先统一一个确认入口，再复用到其他入口；每次使用同一场景回归。
4. 观察一个明确业务窗口后对比指标。若结果改善且没有新增残留，再评估派车/出发流程；若仍存在跨步骤残留，优先调整该流程事务边界。
