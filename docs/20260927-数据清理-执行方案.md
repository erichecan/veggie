## 5. 执行结果（2026-09-27，已在生产库执行，事务已提交）

在正式执行前多做了一步只读核实（dry-run），发现两处如果不处理会导致整个删除事务直接失败或结果偏差，已一并修正：
- **Customer 名单比对**：数据库里有 10 个客户名字带尾部空格（历史脏数据），原始 SQL 用 `lower(c.name)` 比对会漏匹配，导致比对结果比 Python 审计结果多删 4 个、少留 4 个；已改成 `lower(trim(c.name))`，dry-run 复核后与审计数字完全一致才正式执行。
- **StockMove → Lot → Product 的级联链**：`Lot` 删除会被 `StockMove.lotId` 外键（RESTRICT，未设级联）拦住。被删商品名下共有 40 个 Lot、挂着 73 条库存流水记录，若不先清空这批流水，删商品这一步会直接报外键错误、整个事务回滚。已在删 Product 之前先删掉这 73 条流水，其余 2494 条无关流水未动。

## 6. 后续发现并修复的问题（2026-09-27）

### 6.1 演示登录账号失效（已修复）
用"一餐馆身份"登录测试时发现看不到任何商品。排查后发现是内部测试账号 `restaurant1/2@veggie.com`、`restaurant1/2@johnstonebros.ie` 绑定的演示客户 `cust_001`（Achara）被本次清理当作"不在名单"删掉了——这是按规则正确执行的结果，因为 Achara 确实不在 `用户.xlsx` 名单里。`cust_002`（AE D5 demo）经核实清理前就不存在，是更早的遗留问题，与本次无关。已按备份原样恢复 `cust_001`，并按 `lib/seed-customers.ts` 定义补建 `cust_002`（改名"AE D5 (demo)"避免与真实同名客户混淆），两个账号已恢复正常。

### 6.2 波次/托盘/行程残留死数据（已清理）
反馈"配送中心显示很多已排订单，点进去却是空的"。排查确认：`PickingWave.orderIds` 是字符串数组、不是外键，清空 Order 表时不会跟着联动清理，导致 77 个波次里的订单 id 全部变成死引用。进一步排查发现这批脏数据不止影响配送中心一处，还污染了老板总览页、物流分析页、分拣/拣货台、打印中心和一个定时任务（`auto-confirm-departure`）等至少 8 处页面/接口的"订单数"类统计。

由于本次是全库清空 Order，这些引用已 100% 全部失效、没有部分保留的必要，已直接清空：
- `PickingWave`：77 → 0（级联清空关联的 `Pallet` 71 → 0）
- `Trip`：11 → 0（该表本就已知长期未真正使用，见既往记录）

⚠️ 顺带发现一处代码层面的既有薄弱点，本次未修改代码，仅记录：`app/api/dispatch/driver-summary/route.ts` 里的 `orderCount` 直接取 `orderIds.length`，没有像同文件里的 `restaurantCount`/金额字段那样交叉核对 Order 是否真实存在；`app/api/analytics/overview/route.ts`、`app/api/analytics/logistics/route.ts` 也是同样用 `array_length(orderIds,1)` 直接当订单数。这次是数据被清空之后才暴露出来，如果以后再发生"波次订单被外部清理"的情况，这几处会重犯同样的假阳性，是否要顺手把这几处也加上存在性校验，请告知。
