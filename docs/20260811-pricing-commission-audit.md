## 结论

**定价侧健康，提成侧是空转的。**

- 定价：133 万个订单行，`subtotal == unitPrice × orderedQty` **零例外**。税前口径 SSOT 成立。
- 提成：代码完整、商品侧配置完整（5479/5479 都配了件提成价），但 **149,189 张已完成订单的提成金额全是 0**。

## 提成为什么恒为 0 —— 三个输入同时缺

提成 = 件提成 + 客户固定费 + 实送税前额 × 提成率

| 输入 | 状态 | 后果 |
|---|---|---|
| 商品件提成价 | ✅ 5479 / 5479 | 源头是好的 |
| **订单行的提成价快照** | ⛔ **171 / 1,337,568（0.01%）** | 件提成恒为 0 |
| 客户提成率 | ⚠️ 9 / 1605 | 比例提成几乎恒为 0 |
| 客户固定费 | ⛔ 0 / 1605 | 固定费恒为 0 |

**关键在第二行**：商品上明明有提成价，下单时却没快照到订单行上。这不是配置缺失，是**链路缺失**。

## 「无差异」是假性通过

抽最近 20 张已完成单，用 `lib/commission.ts` 重算，与库中值比对：**0 差异**。

但这个 ✓ 不能信 —— 20 张里 20 张是「库中值 0、重算值也 0」。两边相等是因为
三项输入都缺、两边都算出 0，不是因为算对了。**在覆盖率补上去之前，这项比对
不具备任何验证能力。**

这正是「代码存在 ≠ 功能可用」的典型：Stage1-8 全部实现、单测通过、
`db:validate` 也不会报错，但它对 15 万张真实订单产出了 0。

   有没有 `commissionPrice`。

   Z7 修好后第一件事就是补这个受控实验。
2. 若链路已修好：历史 133 万行按「商品当前提成价」回填快照，或与库存一样定一个起算日。
3. 若链路仍在漏：先修代码，回填没有意义（会被继续漏掉的新单稀释）。
4. 客户侧提成率/固定费需要业务方给规则，1605 个客户里只配了 9 个不像是有意为之。
