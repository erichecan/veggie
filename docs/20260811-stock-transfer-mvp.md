# 移仓（库存转移）MVP 规划 · 20260811

> 台账 E2。对应需求原话：「多仓库转移（移仓）：目前这些操作没有界面，也没有完整的
> 产品需求。需要做一个规划，看最小的实现规模是什么样」。
>
> ⚠️ 本文给**两版方案**，选哪版取决于一个你才知道的事实：**客户实际有几个物理仓？**

---

## 一、先把现状说清楚（实查，非推测）

| 事实 | 数据 |
|---|---|
| `Warehouse`（仓库）实体 | **不存在**。全库 52 张表里没有 |
| `Zone`（温区） | 存在，4 个：`FROZEN` / `CHILLED` / `DRY` / `AMBIENT` |
| 温区怎么挂 | **挂在商品上**：`Product.currentZoneId`（该商品实际放哪个温区） |
| 温区覆盖率 | **生产库 5479 个商品，只有 1669 个（30.5%）定位了温区** |
| 库存怎么存 | `Product.qtyOnHand` **单一数字**，不按仓/区分别计数 |
| 库存流水类型 | `IN` / `OUT` / `ADJUSTMENT` / `RETURN` / `SCRAP` —— **没有 `TRANSFER`** |
| 头号不变量 | `qtyOnHand == Σ StockMove.qty`（`db:validate` 第 1 项） |

**最关键的一条**：库存是"每个商品一个总数"，温区只是商品的一个**标签属性**，
不是库存的维度。所以现在系统里**根本无法表达「A 仓有 30 件、B 仓有 20 件」**。

这决定了移仓的实现规模——它不是"补一个界面"，而是**要不要给库存加一个维度**。

---

## 二、两版方案

### 方案甲：轻量版（推荐，若客户只有 1 个物理仓）

**适用**：客户只有一个仓库，内部分冷冻/冷藏/常温几个区，需求实质是
「这批货从冷藏挪到了常温，要有记录」。

**做什么**：

1. `StockMoveType` 新增 `TRANSFER`
2. 新增单据 `StockTransfer`：
   ```
   id / code(TR-00001) / productId / qty
   fromZoneId / toZoneId
   reason / operatorId / movedAt / note
   ```
3. 每次移仓写**两笔** `TRANSFER` 流水（`-qty` 出、`+qty` 入），**净额 0**
   —— 库存总数不变，守恒天然成立；同时把 `Product.currentZoneId` 更新为 `toZoneId`
4. 界面：仓库管理下加一个「移仓」页，选商品 → 选目标温区 → 填数量与原因 → 提交
5. 移仓记录可查询、可导出

**不做什么**（明确划界）：
- 不引入 `Warehouse` 实体
- 不做分区库存计数（仍是每商品一个总数）
- 不做审核流（移仓即生效）
- 不影响成本（同一法人主体内部搬动，不产生成本变化）

**工作量**：1 张表 + 1 个枚举值 + 1 个 API + 1 个页面。**约 1–2 天**。

**代价**：因为库存不分区计数，`fromZoneId` 只能取商品**当前**的温区，
无法校验「冷藏区真的有这么多」。属于**记录型**而非**核算型**移仓。

---

### 方案乙：完整版（若客户真有 2 个以上物理仓）

**适用**：客户有多个物理仓库，需要分别知道每个仓有多少货、能按仓拣货与盘点。

**做什么**：

1. 新增 `Warehouse` 实体，`Zone` 改为隶属于 `Warehouse`
2. **新增 `StockBalance`（仓/区 × 商品 的库存）** —— 这是全部工作量的来源：
   ```
   warehouseId + zoneId + productId → qty
   ```
3. `Product.qtyOnHand` 退化为**派生值** = Σ StockBalance，或直接废弃
4. **所有写库存的路径都要改**：收货、销售出库、报废、盘点、退货、期初——
   每一处都要指明"进哪个仓/出哪个仓"
5. 所有读库存的路径要决定"读总量还是读某仓"：商品列表、缺货判断、
   拣货单、库存预警、盘点、分析中心
6. 移仓单据 + 审核流（跨仓涉及责任交接，通常要审）
7. 成本：跨仓是否分别核算成本（若客户按仓核算，成本模型要一并改）

**工作量**：**2–4 周**，且是**高风险改造**——它动的是库存这个全系统最核心的数。

**必须先解决的前置问题**：
- 存量 133 万订单行、现有库存全部没有仓库归属，**怎么迁**？
- E3 已查出「出库流水只覆盖 0.4% 的已确认订单」，库存流水本身就不完整，
  在这个基础上再加一个维度，**会把不准确放大成不可追溯**

---

## 三、我的建议

**先做方案甲，且先把温区覆盖率补上去。**

理由：

1. **温区功能本身还没铺开** —— 生产库 30.5% 的商品定位了温区，
   剩下 69.5% 连"在哪个区"都不知道。在这个基础上做多仓库，是在没走稳时学跑
2. 需求原话是「**看最小的实现规模是什么样**」，方案甲就是最小可用规模
3. 方案乙动的是库存核心，而库存数据当前的可信度**本来就有问题**（见 E3 报告）。
   应该先把库存流水的完整性修好，再考虑加维度

---

## 四、需要你确认的三件事

1. **客户实际有几个物理仓？** 1 个 → 方案甲；2 个以上 → 需要方案乙，但建议分期
2. **移仓要不要审核？** 方案甲默认不审（即时生效）。若涉及责任交接需要审，请说明
3. **移仓是否影响成本？** 方案甲默认不影响。若客户按仓核算成本，那必须走方案乙

**在这三件事定下来之前，本条不进入开发。** 台账 W3 保持阻塞状态。
