## 确定后的正常流程

1. 司机登记退货，关联原订单行、原因和照片。本次配送的异常与历史货物明确区分。
2. 仓库收到实物并核实：确认实收数量、质量说明、可再售或报废；不同商品需选实际商品并确认基础单位数量。未收到、疑似不是公司的货等情况填写原因后拒绝。
3. 销售查看仓库资料，拒绝、全部批准或按数量部分批准。部分批准/拒绝必须说明原因。批准生成待会计申请，不改变库存或实送量。
4. 会计查看原单、退货照片、仓库实收和质量、销售意见、司机和车牌。确认后原子提交：
   - 实物按仓库实际接收数量处理：可再售回补库存；报废记退回及报废两笔流水，可售库存净不增加。
   - 开票用的净实送量按销售批准数量减少，并重算订单提成。
   - 尚未开票：按调整后的数量生成草稿发票，前提是配送完成且回单已核销、同单所有退货处理完。
   - 已有草稿发票：同步更新数量、税额、总额和余额。草稿还不是已过账的对外会计凭证，不另外创建贷记单。
   - 已过账/已付款发票：原发票金额保持不变，生成并确认有原发票、原订单行来源的贷记单及平衡凭证。已付款情况下保留客户贷项，退款或分配抵扣仍走现有会计操作，不擅自退钱。
   - 同一退货涉及多张有精确来源的发票时逐张生成贷记单；缺少精确来源、金额不匹配或可贷记数量不足时停止并回滚，不能猜测。
5. 会计拒绝时申请留存拒绝记录，退货退回销售重审；重新提交复用同一来源申请，防止重复申请和重复入库。

状态：`WAREHOUSE_PENDING → PENDING_REVIEW → APPROVED（待会计）→ SETTLED（会计已确认）`。仓库/销售拒绝为 `REJECTED`。新增界面将待会计独立显示，不混入已完成。

## 补救及历史货物

- 司机忘记完成配送：沿用调度波次的“完成配送”和共享 `lib/delivery-complete.ts`；会计退货确认要求原配送已完成，避免之后的“完成配送”再覆盖调整过的数量。
- 司机漏报、回单已核销并开票：仓库“车辆检查”中可发起退货，后续走同一仓库→销售→会计流程；已过账走贷记。
- 以前送的货：司机可输入原订单号选商品；没有原单时按商品名、规格、单位、数量、照片登记 `ReturnIntake`。它只代表隔离待核实实物，不是库存入账或退款依据。仓库匹配同一客户的原订单行并核实单位后转为正式退货，或写明原因拒绝。重复匹配被锁定。
- 无来源的历史登记不能指定某张订单，因此不会自动冻结今天这个客户的所有订单。匹配后才按原单拦截；若原单已开票，后续走贷记。
- 收取历史货物的当前趟次与原销售单分开保存。历史退货不抵减当前趟的建议收款。
- 车牌保存在具体波次和 Trip 上，出发后不可覆盖；不是只保存司机现在使用的车牌，换车不会改写历史。

## 需要明确的业务边界

1. **收到货 ≠ 同意退款。** 本实现的部分批准按原订单单位的“批准数量”。例如实收 2 箱，只批准 1 箱退款：实物按 2 箱处理，开票数量减少 1 箱。不是任意金额折让；纯价格折让仍走原有价格贷记申请。
2. **拒绝退款但货已收回**：该实物保留在待处理记录/隔离区，不自动成为可售库存。业务上还需决定返还客户、再次申请审批，或另行授权处理；不能一边拒绝客户退款，一边默认把货卖掉。
3. **质量混合**：同一商品一部分可再售、一部分报废，应分成两条同源退货，不以一种去向概括全部。来源和可退数量仍统一校验。
4. **历史单不能按今天价格退款**：使用原订单/原发票数量与价格，找不到来源先隔离，不凭商品名猜测。原票只有汇总金额、没有可核对的订单行时，系统停止自动处理，由会计核实。
5. **草稿与过账需区分**：已经生成草稿可同步修正；已经过账必须用贷记单，不改写原票。
6. **按要求延迟库存入账**：仓库收到到会计确认之间，货物在隔离区，不计可售库存。若要求“仓库收到即计入隔离库位余额”，需另建隔离库位账；本次没有把待处理货提前放入可售库存。

## 实现保护

- 原订单锁将退货登记、销售处理、会计确认、生成发票/过账串行化；批量锁按订单 ID 排序。
- 会计申请锁加状态检查，重复点击和并发确认只能执行一次；来源键防止重复贷记。
- 会计确认中库存、批次、数量、贷记单、凭证和申请状态一起提交；缺科目、来源不明、数据库写入失败均回滚。
- 有成本的退货要求库存估值凭证成功，不允许静默漏掉估值分录。
- 回单核销可以记录事实；有未决退货时不能顺便改数量。退货已调整过数量后，也不能经回单入口再次减量。
- `fillDeliveredQtyIfUnrecorded` 不再把全部退完后的 0 数量误补为原下单数量。
- 旧一键贷记生成器只处理 v1 已批准记录，不能抢走 v2 待会计记录。
- 原有 `workflowVersion=1` 已批准/已结算记录已经产生过库存效果，迁移不重放。未处理、缺验收资料的旧正式退货回到仓库补核实。
- 没有原订单行的旧 Trip JSON 不自动猜测匹配/入账，专用销售写入口已停止处理这种不确定来源；需核实原单后登记，历史原数据保持可读。

## 权限变化

- 有仓库核实权限的人员可以登记漏报退货（`POST /api/order-returns`），不会因此取得销售审批或会计确认权限。
- 司机可以在自己的趟次读取退货/匹配来源（`GET /api/trips/:id/returns`），服务端检查当前司机身份和本趟客户。
- 新待匹配登记处理端点 `PUT /api/order-returns/intakes/:id` 仅仓库核实权限。
- 这些是有意变更，已同步权限规则和快照；没有修改账号生产权限配置。
