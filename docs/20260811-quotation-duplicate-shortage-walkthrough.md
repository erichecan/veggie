# 创建 Quotation 的重复/缺货提醒走查 · 20260811

> 台账 B1。浏览器真实操作（生产构建 + 本机 veggie_test），账号 `operator@veggie.com`。
> 对应需求原话：「创建 Quotation 时，重复商品及缺货商品的提醒，需要看一下 UI 交互的显示是否合理清晰」。

## 结论：这两个提醒做得很好，三种场景均通过

三种场景各构造一次实测：

| 场景 | 表现 |
|---|---|
| 仅重复 | 🔁 紫色横幅「重复商品提醒：1 个商品被重复添加 (Shanghai Pachoi 8Kg ×2) — 可点右侧「合并」合并为一行（数量相加），或保留现状手动调整」+ **「合并重复项」按钮** |
| 仅缺货 | 🚨 红色横幅「库存警告（基于可承诺量）：1 个商品无可用库存 (Red Heera Peanut Butter (Smooth) 340g Jar)」 |
| 两者兼有 | 两条横幅**并列显示、颜色区分、互不干扰** |

**指明具体行与商品** ✅ —— 不只横幅里写了商品名与重复次数，**行级也有标记**：
重复行的序号旁有 🔁 图标，缺货行**整行标红**并带 🚨。

**能否继续保存** ✅ —— 实测点 Save 成功保存、退出编辑态、无阻断。重复提醒的文案
「或保留现状手动调整」也明说了这一点。设计上是**告知而非阻断**，合理：缺货可能
中午就补上（这正是需求里「人工跳过」那条的场景）。

缺货判定口径标注清楚（「基于可承诺量」ATP = 库存 − 其他订单待发量），低库存
（ATP < 20）另用琥珀色区分并显示具体 ATP 数值。

## 一个设计上的取舍值得确认

**ATP 只与固定阈值（0 和 20）比较，从不与「本行下单量」比较。**

即：某商品 ATP = 500，客户下单 10000 个 —— **不会有任何警告**，因为 500 > 20。

这是有意为之还是遗漏，需业务确认。若要覆盖，判据应改成 `atp < 本行 orderedQty`。

## 走查中发现的量纲问题（已修）

### 事件种子把税率按**小数**写进订单行，与代码 SSOT 相反

保存后核对落库，发现同一张单里出现两种量纲：

| sequence | 来源 | taxRate |
|---|---|---|
| 0–2 | 事件种子 | **0.1350** |
| 3–4 | 本次界面新增 | **13.5000** |

代码的 SSOT 是**百分数**，三处按 `taxRate/100` 计算：
`lib/analytics/metrics.ts`、`lib/order-items.ts`、`lib/order-pdf.ts`。
按小数存的行在这三处算出的税额只有真实值的 **1/100**，而 `db:validate` 不校验
税额，所以一路绿灯。

修法：在 `personas.ts` 源头归一，并同步下游 **5 处**税额计算
（`scenarios.ts`、`billing.ts`、`purchase.ts` ×2）—— 只改源头不改下游，
税额会反过来涨 100 倍。修复后测试库小数行 **1444 → 0**，8 项守恒断言与
11 项不变量全部保持通过。

## 附带查明：生产库 99.4% 的订单行税率为 NULL

只读探测 Neon 生产副本：

| 量纲 | 行数 |
|---|---:|
| **NULL** | **1,330,196（99.4%）** |
| 0 | 6,825 |
| 百分数 (≥1) | 536 |
| 小数 (<1) | 11 |

两点结论：

1. **百分数确实是主流约定**（536 vs 11），A2 的修复方向正确
2. **但 133 万行是 NULL** —— A2 只修了门户新单的写入路径，存量完全没动。
   这不是门户独有的问题，是全局的

⚠️ 需要业务确认：这些 NULL 行的税额在开票时怎么算？发票接口
（`app/api/invoices/route.ts:132`）对 NULL 会取 0。若历史发票都是这么开出去的，
可能存在系统性少计税——**这一条超出 B1 范围，已记入台账待专项核查**。
