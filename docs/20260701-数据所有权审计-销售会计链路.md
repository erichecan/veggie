## 一、总体诊断

第一轮（6/24）的 P0/P1 病灶**大部分已闭合**（见第五节「已闭合」）。本轮发现的核心债，是 **commit `562df3b`「price field unification」把金额口径从「含税」翻转为「税前」时，只改了一部分写入点和 UI，留下三类漂移**：

## 三、订正脚本范围（A-1 + A-2）——先 dry-run，确认数字再写库

> ⚠️ 用户 DB 在云端，脚本连云端库、**先只读统计**（dry-run），把「将改多少行、样本前后值」打出来，用户确认后才写。

### 3.1 判别新旧口径的依据

| 信号 | 旧口径（562df3b 前） | 新口径（562df3b 后，2026-06-28 13:44 起） |
|---|---|---|
| `OrderLine.taxRate` | 小数：0 / 0.048 / 0.09 / 0.135 / 0.23 | 百分数：0 / 4.8 / 9 / 13.5 / 23 |
| 判别式 | `0 < taxRate < 1` → 旧 | `taxRate ≥ 1` → 新 |
| 歧义值 | `taxRate == 0`：两口径同值，**无需改**（税额恒 0） | 同左 |
| `Order.totalAmount` 口径 | 含税 or 税前（视该单是否被 PUT 改过，混乱） | 应为税前 |

爱尔兰 VAT 档位 0 / 4.8 / 9 / 13.5 / 23 —— 小数区间 (0,1) 与百分数区间 [4.8,23] **无重叠**，判别无歧义（除 0，而 0 不需改）。

### 3.2 脚本要做的订正（确定性、可重算，低二次订正风险）

1. **`OrderLine.taxRate` 归一到百分数**：对 `0 < taxRate < 1` 的行 `taxRate = taxRate * 100`。`taxRate ≥ 1` 或 `== 0` 跳过。→ 幂等：跑第二遍不会再命中（已 ≥1）。
2. **`OrderLine.subtotal` 校正到税前**：`subtotal` 应恒等于 `unitPrice × orderedQty`。直接**重算** `subtotal = round(unitPrice*orderedQty, 2)`，与新旧无关、无二次订正风险（幂等）。
   - ⚠️ 前提：历史 `unitPrice` 是否曾存含税？需 dry-run 抽样核对 `unitPrice×qty` vs 现存 `subtotal` 的差是否恰好一个 VAT 倍数——若是，说明历史 unitPrice 也含税，需额外一步 `unitPrice /= (1+rate)`。**这一步存疑，dry-run 必须打样本供人工判断，不可盲改。**
3. **`Order.totalAmount` 重算为税前**：`totalAmount = Σ(round(unitPrice*orderedQty,2))`（=Σ税前 subtotal）。幂等、确定性。

### 3.2b dry-run 实测确认（2026-07-01，云端库只读）

脚本 `scripts/fix-tax-pretax-unification.ts` dry-run 结果（813 单 / 7063 行）：

- **`OrderLine.subtotal` 漂移 = 0 行**：全库 subtotal 无一例外 = `unitPrice×qty`，疑似含税 0 行 → **实测坐实：unitPrice/subtotal 一直是税前，订正无需对 unitPrice 除税**（第五节存疑项已消除）。
- **`OrderLine.taxRate`**：513 行旧小数（仅 0.135 / 0.23），6 行已百分数，6544 行为 0；取值集合 `{0,0.135,0.23,23}` 无歧义值。→ 513 行 ×100 归一。
- **`Order.totalAmount`**：274/813 单 ≠ 税前。其中 **250 单 ≈ 含税**（A-2 混存，重算即订正）；**24 单 = A-4**（见下）。

### A-4（新发现）：24 单 `Order.totalAmount` 陈旧，与当前行之和不符

与税口径无关的独立病灶：`totalAmount ≠ Σ当前行 subtotal`，成因是**改单删行后 totalAmount 未重算**。细分：

- **2 单有金额但 0 行**：`D151864`(LOCKED €17.5)、`D152247`(**IN_DELIVERY €694**) — 行被删光/未建，总额残留。IN_DELIVERY 无行为真异常。
- **~22 单总额 > Σ当前行**：如 `D151570` 现 112.5 vs 单行 23.5、`D152032` 现 2389.3 vs 27 行 2332.3。多为 LOCKED 已锁定历史单；少数（D151953/D151834/D151512）实为含税仅差 1~3 分舍入。

**处置需 owner 拍板**：按 SSOT「总额=行之和」重算成税前是正确的，但会显著改动 LOCKED 历史单金额、并把 2 单归零 → 属动生产历史数据。选项：(A) 连这 24 单一起重算（彻底 SSOT）；(B) 本次只订正 250 单干净含税 + 513 taxRate，24 单单独复核（尤其 IN_DELIVERY 0 行那单要查为何在配送）。
