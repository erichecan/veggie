## 二、生产库实测：三条流水线的真实运转情况

```
Trip 表全部历史：11 条，settlementStatus 全部是 pending，status 从未出现过 COMPLETED
DriverDailyReport 表：0 条（从未有司机提交过日报）
Order.orderReturn = true：全库 149,930 条订单里，0 条（不分状态，一条都没有）
Payment 表：0 条
```

**结论（数据事实，非推测）**：
- "司机交账"从未有一条 Trip 走完 pending → confirmed 的完整流程；财务端的"已确认"Tab 永远是空的。
- "司机对账"依赖的 `DriverDailyReport` 表从来没有任何一条记录；财务端"已提交/已确认"Tab 永远是空的。
- "会计核销"这个布尔字段从建库以来从未被真正标记为 true 过——现在这套扫码/批量核销 UI 虽然功能完整，但没有留下过一次真实使用痕迹。

三条流水线目前在生产数据层面都接近空转。**这是一个需要你确认的事实**：是这三个功能确实没人在日常用（比如司机现金结算走的是线下/微信转账，公司没强制走这个系统），还是应该有人在用但流程在某个环节断掉了、大家绕过去了？这决定了接下来该先补完"钱"这条线，还是可以先放着、优先把你现在最需要的"核销"这条线做扎实。

## 三、概念区分

### (a) 交账 vs 对账

代码作者自己把这两者定义成**同一件事的两种视图**（`app/api/driver-reports/summary/route.ts` 注释原话："与交账是同一件事的不同视图，另开权限点只会得到一个没人有的开关"），区别只在聚合粒度：
- 交账：按**单次行程（Trip）**记录，司机跑完一趟车，把这一趟收的现金/在线收款金额提交一次。
- 对账：按**司机 × 业务日**聚合，把当天这个司机跑的所有行程汇总成一天的总数，财务拿"司机自己申报的总数"和"系统按 Trip 算出来的总数"做比对，对不上的标红。

问题在于：这两个"视图"被实现成了**两套完全独立、互不通信的页面 + API + 状态机**，而不是一份数据的两种展示方式。财务端两个页面分别有自己的 pending/submitted/confirmed 状态流转，司机端一个"交账"页面里，上半段在喂对账系统（`DailyReportCard` 组件，POST 到 `/api/driver-reports/daily`），下半段在喂交账系统（逐条提交 `POST /api/trips/[id]/settlement`），彼此不知道对方的存在。这就是你说的"多处重叠且嵌套"的具体来源。

### (b) 交账/对账 vs 会计核销

这两组东西关心的**对象完全不同**：
- 交账、对账关心的是**钱**——司机手上收的现金/在线收款，和系统里应收金额对不对得上。
- 会计核销（`/classic/accounting`）关心的是**单**——这张送货单的纸质凭证有没有物理送回仓库，跟金额、收款完全无关，只是一个"回/没回"的布尔状态。

另外还发现一个容易混淆的地方：交账确认时会触发 `lib/trip-settlement-payment.ts` 里的 `postTripCollections()`，把司机交的钱核销到客户发票上——这也叫"核销"，但核销的是**发票金额**，跟 `/classic/accounting` 页面核销的**送货单回收状态**是两个完全不同的东西，只是共用了"核销"这个词，容易和你现在问的这个页面搞混。

## 四、会计核销：现状 vs 你描述的期望交互

你的期望：扫码 → 命中变色标记"已选中" → 选中行出现"确认/Return"操作 → 没扫到的行保持原样代表"没回"。

现状（`app/[locale]/classic/accounting/page.tsx`）逐点对比：

| 环节 | 你的期望 | 现状 |
|---|---|---|
| 扫码比对范围 | 跟"今天所有送出去的单"比对 | 集合来自 `GET /api/orders?status=CONFIRMED,WAVE_ASSIGNED,COMPLETED,IN_DELIVERY`，默认按创建时间倒序**只取最近 500 条**，再前端按送货日期过滤"今天"；因为生产库里订单从 IN_DELIVERY 直接跳 LOCKED（COMPLETED 状态实际 0 条使用），且 500 条截断可能漏单，页面又另外叠了一个"按时间段查漏单"面板去补漏——这本身就是"今天送出去的单"这个集合定义不清晰、两条取数口径不一致的表现 |
| 扫中即选中变色 | 是 | 是，扫中会加入勾选 + 2 秒高亮（`flash` 效果），但**只存在前端 state，刷新即丢，不落库** |
| 选中后出现"确认/Return" | 选中是中间态，还要再点一步才算数 | 现状没有中间态：勾选之后要额外点「批量核销」或行内「核销」按钮，**点击立即写库生效，没有二次确认弹窗**；也没有"Return"这个动作——现在唯一的"退回"语义（退回重交）长在司机交账页面，针对的是 Trip 而不是订单，是完全不同的一套代码 |
| 未选中=没回 | 是（默认状态） | 是，`orderReturn` 默认 false 就是"没回"，逻辑上一致 |

需要你确认清楚以后再定：
1. 你说的 "Return"，具体代表什么业务含义？是"这张单其实还没送到，扫错了/不该出现在今天这个列表里"，还是"这张单送回来了但有问题（比如东西少了、单据字迹不清），要退回给司机核实"？这两种含义对应的系统状态完全不同，需要新增字段还是只是撤销勾选，取决于这个。
2. 扫中之后是希望"直接算已核销"（一步到位，效率优先），还是"先进入待确认的中间态，会计还要再点一次确认才真正核销"（防止扫码枪误触/重复扫描）？你原文列的 (b)(c) 两步分开写，听起来是后者，但想跟你确认一下这是不是故意要两步。
