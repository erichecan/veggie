# Phase 1 范围建议 — 三项建议延后到二期

> 2026-08-02。依据：`docs/audit-evidence/20260802-results.json` 的探针复核结果。
> 本文件是**给甲方讨论用的范围说明**，不是单方面缩减范围的通知。
> 三项均在合同功能清单内，我方建议延后，理由与替代方案如下，最终由甲方决定。

⚠️ 重要：这三项在核实报告里的判定**仍然保持「未完成 / 部分完成」**，不因为"建议延后"
就改成"范围外"。报告要如实反映系统现状，范围怎么定是另一件事。

---

## 一、组织架构：多公司 / 多部门 / 多门店（合同模块 9）

**当前状态**：`Company` / `Department` / `Store` / `Branch` / `Organization` 五个模型全不存在，
系统是单公司单仓库架构。

**建议**：延后至二期。

**理由**：

1. **业务上没有第二个组织**。甲方目前是单一法人、单一仓库、单一门店的实体经营。
2. **改造面极大**。多组织不是加一张表，而是要给几乎所有业务表加组织外键
   （Order / Customer / Product / Lot / StockMove / Invoice / VendorBill …47 个模型里大半），
   并把权限模型从「角色」升级为「角色 × 组织」。已有 149,874 单、133 万行订单明细需要回填归属。
3. **收益为零而风险为负**。做出来的是一个所有记录组织字段永远等于同一个值的维度，
   却要为它承担全库回归风险。

**如果二期真要做**，建议届时一并解决多仓库（下条），两者共用同一套组织树，不要分两次改。

**替代方案**：在《项目验收单》里写明「Phase 1 为单组织架构，多公司/多部门/多门店为二期范围」。

---

## 二、多仓库调拨（合同模块 5）

**当前状态**：`Warehouse` 模型不存在；调拨相关关键词全库零命中。
现为「单仓库 + 多温区（Zone）」架构，四个温区（冷冻 -18°C 以下 / 冷藏 0~4°C / 常温干货 / 常温超市）
均已实现，1669 个商品已归温区。

**建议**：延后至二期，与上条一并做。

**理由**：

1. **没有第二个仓库**。调拨的前提是至少两个库存地点。
2. **多温区已覆盖真实业务**。合同这一条的原文是「实时查看**各仓库**、各商品库存数量、
   安全库存、库存预警，支持多仓库调拨」——前半句（实时监控、安全库存、库存预警）**已完整实现**，
   缺的只有跨仓调拨这半句。
3. 建 `Warehouse` 实体等于给单仓业务加一层恒为 1 的维度，所有库存查询都要多一次关联。

**替代方案**：验收单写明「Phase 1 为单仓库多温区架构；库存实时监控与预警已交付，
多仓调拨随二期多组织一并实现」。

## 三、第三方标准 API 接口（合同模块 10）

**当前状态**：157 个 API 路由全部服务于自家前端，统一走 JWT session 鉴权。
面向第三方的 API Key / OAuth / webhook / 版本号前缀均零命中；
合同点名的对接对象（ERP / 财务系统 / 电子秤 / 税控盘 / 物流平台）也全库零命中。

**建议**：延后，直到有明确的对接方。

**理由**：

1. **目前一个确定的对接对象都没有**。合同写的是"预留标准 API 接口，**可对接**第三方…"，
   但没有指定要对接哪家 ERP、哪家物流、什么型号的电子秤或税控盘。
2. **没有对接目标的接口设计大概率白做**。第三方集成的形态高度依赖对方：
   对方是拉还是推、认证走 API Key 还是 OAuth、数据格式、字段映射、错误重试语义——
   这些全部由对方决定。凭空设计一套，等真对接时基本要推倒重来。
3. **安全面显著扩大**。对外开放 API 意味着新增一整套密钥管理、限流、审计与轮换机制。
   本次审计刚发现并修复过一处白名单误配导致全量客户名册匿名可读
   （见 `docs/20260802-contract-feature-audit-tasks.md`），在没有真实需求前扩大攻击面不划算。

**替代方案（建议写进验收单）**：

- Phase 1 交付「具备对接能力的架构基础」：所有业务能力已经是 REST 接口 + 统一鉴权闸门，
  新增对外通道时只需在现有路由外包一层认证适配，不需要重写业务逻辑。
- 甲方明确对接方（哪家 ERP / 哪家物流 / 什么秤）后，按实际协议单独立项。
- 合同已单列的 **PDA 扫码**与**电子秤**两项本就是「条件触发后免费升级」，
  与本条一并等触发条件成就。
  （注：PDA 那条的触发条件是"仓库全部商品都有打印条码"，实测条码覆盖率 **0/5482**，尚未成就。）

## 三项合计对完成度的影响

若甲方接受延后，这三项从 Phase 1 计分口径中移出后：

| 口径 | 计分项 | 加权完成度 |
|---|---|---|
| 当前（三项计入） | 55 | 57.3% |
| 三项移出后 | 52 | 约 60.6% |

差值不大——说明这三项本来也不是完成度的主要缺口。
**真正的缺口在别处**（司机端签收链路、财务报表、采购质检等），
这些正在按 `docs/20260802-gap-closure-tasks.md` 的波次逐条补齐。

列出这个数字是为了说明「延后这三项不是为了让报表好看」。
