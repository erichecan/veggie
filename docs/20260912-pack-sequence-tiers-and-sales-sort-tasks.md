## 已确认的产品决策

1. **分层方向**：1 = 最下面（重 / 不怕压，最先装）……4 = 最上面（轻 / 怕压，最后装）。与现有代码注释
   "数字越小越先装/放最下（重）；越大越后装/放最上（怕压）"方向一致，只是把自由数字收窄成 1-4。
2. **基础单位默认值 0**：排在 1-4 最前面，当成比 1 更早装的一档——即"没特意设分层的商品"是整单
   最底层的基础货，1-4 是需要特殊摆放的商品，从重到轻往上叠。
3. **商品详情页控件**：4 个数字按钮（1/2/3/4）单选高亮；再点一次已选中的按钮 = 取消选中，
   值变回 0（基础）。不单独暴露"0"这个按钮。

## 现状（调研结论，已验证）

- `ProductSaleUom.sequence`（`prisma/schema.prisma:433-436`）：`Int?`，无 `@default`，无范围校验，
  自由数字。本地开发库实测：5 条记录，3 条 null、1 条 `5`、1 条 `50`——历史脏数据确实存在，
  迁移不能假设"反正都是空的"。
- 生产库同一分布**没能实测确认**：SSH 到 droplet 后 `sudo -u postgres psql` 密码验证失败（尝试了
  两次都被拒），放弃继续重试。因此下面的迁移设计按"任意历史分布都安全"来写（收拢式 clamp），
  不依赖具体生产数字；但正式对生产跑迁移前，建议先用只读 SELECT 在生产预检一次实际会被
  收拢的行数，不要盲跑。
- 拣货单打印排序（`lib/print/line-sort.ts` + `lib/print/uom-sequence.ts`）已经在用这个字段升序
  排序、null 排最后——**排序逻辑本身不用改**，null 变成 0 之后自然排最前，符合决策 2。
- 列表页"Pack Sequence"列当前 `sortKey: 'saleUnitsCount'`（`products/page.tsx`）实际排的是
  "可售单位数量"，跟这个 sequence 值毫无关系——是个挂羊头卖狗肉的假排序，这次要改成真排序。
