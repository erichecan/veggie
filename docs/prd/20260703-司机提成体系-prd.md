# 司机提成体系 PRD

> 版本：v1.0 · 2026-07-03
> 状态：待评审 → 待实现
> 关联：昨天（2026-07-02, commit `631b408`）从前端移除了 Cms 显示列。本 PRD 在此基础上把「提成」从一个被误当作展示字段的东西，正本清源为**发给司机的工钱**这一核心业务数据。

---

## 1. 背景与问题

### 1.1 提成到底是什么

提成 = **司机送完一单，老板要付给他的工钱**。它不是一个"比率""参考值"或"界面上的装饰列"，而是**一笔实实在在、要发出去的钱**，必须落在每一单上、记录在案。

### 1.2 昨天错在哪（教训，写进 PRD 以免重犯）

- 昨天把 Cms 当成"界面太挤的展示噪音"删掉了显示列（`631b408`）。**定性错误**：提成是钱，不是装饰。
- 更早的隐患：订单创建 API 在 `create OrderLine` 时**从未写入 `commissionPrice`**（`app/api/orders/route.ts:324-338`），即商品件提成快照这条链路**在后端本就是断的**。
- 根本原则：**"前端不显示" ≠ "后端不记录"。** 显示可以藏，但采集、计算、快照、落库必须照常，甚至更严格。

### 1.3 为什么必须冻结快照

商品的件提成、客户的辛苦费/抽成率，今天可能改、明天可能调。若不冻结，等月底给司机结工资时"实时重算"，用的是改过的新价，账就对不上，司机会拿错钱。

**正确做法：在送达那一刻，把算好的提成金额作为快照写死在这一单上。** 以后无论商品价、客户费怎么变，这一单的钱永远不变。

## 2. 核心计算规则

### 2.1 公式（纯加法，每一项可单独核对）

```
一单司机提成 =
    Σ ( 商品件提成 × 实送数量 )          ← 商品维度（cms_item）
  + 客户固定辛苦费                        ← 客户维度·固定（cms_customer 固定项）
  + 送达税前额 × 客户抽成率               ← 客户维度·抽成（cms_customer 抽成项）
```

- **商品件提成**：绑在每个商品上的每单位提成额（大米一袋提成高、小番茄一盒提成低）。
- **客户固定辛苦费**：送这家客户一趟的固定加价（搬楼、地下室、密码门、男停车等麻烦事），**与订单金额、数量无关**，去一趟就是一笔。
- **客户抽成率**：按送达金额的百分比抽成，客户单子越大司机拿越多，是另一激励维度。

> 客户提成 = 固定辛苦费 + 抽成，两者**相加**（不做加权平均）：量纲不同、语义不同，相加后每一项含义清晰、可分项打印核对。

### 2.2 冻结时点与数量口径

- **冻结时点**：**订单送达（配送完成）那一刻**。此刻把提成算出并写死快照。
- **数量口径**：**按实际送达量 `deliveredQty`**，不是下单量 `orderedQty`。
  - 例：客户开 10 箱、缺货实送 8 箱 → 商品件提成按 **8** 箱算。司机只为实际搬的货拿钱。
  - 客户固定辛苦费**不受数量影响**，只要这单成行送达就计一笔。
  - 抽成基数用**送达税前额**（实送量 × 税前单价），与商品件提成的数量口径保持一致。
- **税口径**：抽成基数用**税前额**（与现有 CMS 口径一致：CMS 考核司机工作量、不含税，见 `finance/page.tsx:113` 注释）。

### 2.3 边界情况

| 场景 | 处理 |
|---|---|
| 订单未送达（PENDING/CONFIRMED/配送中） | 提成快照**尚未冻结**，`driverCommissionTotal = null`；页面可显示"预估提成"（实时算），但不入账 |
| 整单取消/退货 | 不冻结提成；已冻结的随单状态作废 |
| 某商品件提成为空/未设置 | 该商品件提成按 0 计，不阻断整单 |
| 客户未设固定费/抽成率 | 对应项按 0 计 |
| 实送量为 0（整单缺货未送） | 商品件提成为 0；**客户固定辛苦费也不计**（没去成就没有辛苦费） |
| 送达后又修改了送达量（如退货审核减 `deliveredQty`） | 重新计算并覆盖快照（以最终送达量为准，需留审计） |

## 3. 数据模型

### 3.1 命名约定

**不重命名数据库字段**（避免大迁移 + 全代码改），沿用现有 Prisma 字段名；在 **UI 文案和文档口径**上统一用 `cms_item` / `cms_customer` 概念表述。

| 业务概念 | 口径叫法 | 数据库字段 |
|---|---|---|
| 商品件提成 | cms_item | `Product/ProductTemplate.commissionPrice` |
| 客户固定辛苦费 | cms_customer·固定 | `Customer.commissionFixed` |
| 客户抽成率 | cms_customer·抽成 | `Customer.commissionRate` |

### 3.2 字段盘点与改动

| 数据 | 字段 | 现状 | 本次改动 |
|---|---|---|---|
| 商品件提成（主数据） | `Product/Template.commissionPrice` | ✓ 可编辑 | 无 |
| 客户固定辛苦费（主数据） | `Customer.commissionFixed` | ✓ 可编辑 | 无（确认客户编辑页已可填） |
| 客户抽成率（主数据） | `Customer.commissionRate` | ✓ 可编辑 | 无 |
| 商品件提成·订单行快照 | `OrderLine.commissionPrice` | ⚠️ 字段在，**下单未写入** | **下单时写入下单快照；送达时按实送量确认** |
| 客户抽成率·订单快照 | `Order.commissionRate` | ✓ 下单已写入（orders/route.ts:315） | 无 |
| 客户固定费·订单快照 | *(无)* | ✗ | **新建 `Order.commissionFixed Decimal?(10,2)`** |
| **每单最终提成金额** | *(无)* | ✗ | **新建 `Order.driverCommissionTotal Decimal?(12,2)`（送达时冻结）** |
| 提成冻结时间 | *(无)* | ✗ | **新建 `Order.commissionFrozenAt DateTime?`** |
| 配送司机总佣金 | `Trip.driverCommission` | ✓ 存在 | 口径对齐为「该 Trip 下各单 `driverCommissionTotal` 之和」 |

### 3.3 新建字段定义

```prisma
model Order {
  // ...existing...
  /// 客户固定辛苦费·下单快照（EUR/单，来自 Customer.commissionFixed）
  commissionFixed        Decimal?  @db.Decimal(10, 2)
  /// 每单最终司机提成金额（EUR）——送达时按实送量冻结，发工资/单笔盈亏/利润分析共用此数
  driverCommissionTotal  Decimal?  @db.Decimal(12, 2)
  /// 提成冻结时间（送达确认时写入，用于判定是否已入账）
  commissionFrozenAt     DateTime?
}
```

> 迁移方式遵循项目惯例（`prisma-migration-shadow-db` 记忆）：`db push` + 手写迁移 + `migrate resolve`，避免 shadow DB 重放旧迁移失败。

## 4. 下游消费者（三者读同一个冻结数）

冻结后的 `Order.driverCommissionTotal` 是唯一真相源，以下三处**都读它、不各自重算**：

1. **司机工资结算**（`driver/settlement`、`finance` 佣金卡）：某司机某周期内所有已送达订单的 `driverCommissionTotal` 求和 = 应发工钱。
2. **单笔盈亏**：单笔利润 = 销售毛利 − 提成（提成是成本项）− 其他成本。
3. **利润分析**（`boss/sales-analysis`、数据分析中心）：整体利润扣减司机提成成本，口径与结算一致。

> 现有 `finance/page.tsx:110-122` 的 `completedTotal × commissionRate` 是**旧的、不完整的**口径（只算了客户抽成、漏了商品件提成和固定费），须替换为读 `driverCommissionTotal`。

## 5. 前端显示规则

**原则：下单操作页隐藏，结算/老板页显示。后端全程记录。**

| 页面 | 提成显示 | 说明 |
|---|---|---|
| 下单页 `place-order` | ❌ 隐藏 | 保持昨天的改动，不显示 Cms 列 |
| 报价单详情 `quotations/[id]` | ❌ 隐藏 | 同上 |
| 销售单详情 `orders/[id]` | ❌ 隐藏 | 同上 |
| 司机结算 `driver/settlement` | ✅ 显示 | 显示每单提成、汇总工钱 |
| 财务佣金 `finance` | ✅ 显示 | 佣金卡改读 `driverCommissionTotal` |
| 老板销售分析 `boss/sales-analysis` | ✅ 显示 | 利润口径扣提成成本 |

> 结算/老板页应能**分项展示**：商品件提成小计 / 客户固定费 / 客户抽成 / 合计，便于向司机解释每笔钱怎么来的。

## 6. 验收标准

- [ ] 下单创建订单时，`OrderLine.commissionPrice` 写入商品件提成快照（当前缺失，必须补）。
- [ ] 下单创建订单时，`Order.commissionFixed`、`Order.commissionRate` 均快照客户当时的值。
- [ ] 订单送达（配送完成）时，按实送量 `deliveredQty` 计算并冻结 `Order.driverCommissionTotal` 与 `commissionFrozenAt`。
- [ ] 冻结后修改商品件提成/客户费/抽成率，历史订单的 `driverCommissionTotal` **不变**。
- [ ] 缺货少送（实送 < 下单）时，商品件提成按实送量计；整单未送达则不计客户固定费。
- [ ] 退货审核减少 `deliveredQty` 后，该单 `driverCommissionTotal` 重算覆盖。
- [ ] `finance` 佣金金额 = 司机名下已送达订单 `driverCommissionTotal` 之和，与旧口径切换后数值可解释。
- [ ] `Trip.driverCommission` = 该 Trip 下各单 `driverCommissionTotal` 之和。
- [ ] 下单页/报价单/销售单详情**不显示**提成；结算/财务/老板页**显示**且可分项。
- [ ] 单笔盈亏、利润分析扣减的提成成本 = `driverCommissionTotal`（三处同源）。

## 7. 非目标（YAGNI）

- 不重命名数据库字段（仅统一 UI/文档口径）。
- 不做提成的多档阶梯、时段加成、绩效系数等复杂规则（本期只做"件提成 + 固定费 + 抽成"三项相加）。
- 不做司机之间的提成分成/拆账。
