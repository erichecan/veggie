# 司机归档后，有些地方还能读取到司机 —— 需求原话

## 用户原话（20261017，附截图批注）

> 你看,客户反馈,司机归档后,有些地方还是能读取到司机,全面的排查一下这个问题

截图：客户反馈，编辑某条记录时，下拉框里仍能看到已归档的司机「yang / Yunzhi Yang」。

## 排查范围与结论

对全仓库每一处读取 `DriverSlot` 的代码路径逐一分类：

- **历史报表类（判定：正常，不是 bug）**：司机提成考核、调度交账、历史日报等统计/审计路径，按设计必须保留归档前的历史快照（否则历史单子的司机信息会"凭空消失"），**不应该**过滤掉已归档司机。
- **当前可选项类（判定：bug）**：所有"选司机"的下拉框/托盘 lane，理应随归档实时消失，但发现 4 个独立成因：

### 1）订单编辑页 `app/[locale]/classic/operator/orders/[id]/page.tsx`
司机下拉列表只在页面首次加载时拉取一次，开着这个页面挂一整天，期间别人把司机归档了也不会刷新。
修复：补充 `useRefetchOnFocus`，切回这个标签页时静默重拉最新司机列表。

### 2）报价单编辑页 `app/[locale]/classic/operator/quotations/[id]/page.tsx`
同上，同一种成因，同一种修复。

### 3）调度台 `app/[locale]/classic/operator/dispatch-console/_components/BatchTab.tsx`
调度台常年开着不换日期，之前完全没有"切回标签页自动刷新"的机制，司机被归档后托盘 lane 不会自己消失，必须手动换日期才会重新拉取。
修复：补充 `useRefetchOnFocus`，静默重拉（不触发整页 loading 闪烁）。

### 4）后端归档接口 `app/api/driver-slots/[id]/route.ts`（根因，影响最大）
`Customer.defaultDriverSlotId` 关联 `DriverSlot` 时 schema 写的是 `onDelete: SetNull`，但归档走的是 `UPDATE ... SET archived = true`（软删除），**不是硬删除**，`SetNull` 这条级联规则从未触发过。
结果：客户档案上一旦设置过"默认司机"，司机被归档之后这个字段永远不会自动清空，下次编辑这个客户的订单时，后端会把这个已归档司机的 id 原样读出来显示。
两个归档入口（`PUT .../archived` 分支、`DELETE` 的 `archiveSlot`）都补了同一行：归档时顺手把所有指向它的 `Customer.defaultDriverSlotId` 清空。

## 生产数据核实与处理

用只读 SQL 在生产库核实这条根因是否有真实受害者：

```sql
select c.id, c.name, c."defaultDriverSlotId", ds."driverName", ds.archived
from "Customer" c
join "DriverSlot" ds on ds.id = c."defaultDriverSlotId"
where ds.archived = true;
```

查到 5 条真实存量脏数据（修复上线前产生，新代码不会再新增）：

| 客户 | 残留指向的已归档司机 |
| --- | --- |
| Akayu Mullingar | ASHWIN |
| Double Y Athlone | ASHWIN |
| Apache Pizza & Peking Offaly | ASHWIN |
| Green Mango & Summer Inn D14 | Moazzam |
| Akayu-Portlaoise | hanhua |

已在生产库执行一次性回填，把这 5 条的 `defaultDriverSlotId` 清空（逻辑与新代码归档时做的事完全一致，只是补做历史存量）：

```sql
update "Customer" c
set "defaultDriverSlotId" = null
from "DriverSlot" ds
where ds.id = c."defaultDriverSlotId" and ds.archived = true;
```

执行结果：`UPDATE 5`。这 5 个客户不会丢失任何业务记录——只是清掉一个"默认司机"的快捷设置，下次编辑时和没设置过默认司机的客户一样，正常手选即可。
