## 模块拆解

### 模块 A：商品分类三级化

**现状**（已调研）：`ProductCategory` 是纯一级扁平表（`prisma/schema.prisma:232-247`，无 `parentId`），本地库 33 条记录，`Product.categoryId`（`:325-326`）单选单层，本地库覆盖率 100%（5480 条——生产库规模不同，迁移前需复核）。配置入口在 `app/[locale]/classic/operator/settings/page.tsx`，`ProductCategorySection`（约 `:489-650`），和"计量单位"是设置页里的同级 tab（不是嵌套在"计量单位"里面，只是 UI 上容易被当成附属）。

全站 40+ 处用 `categoryId` 做筛选/分组/定价（商品 CRUD、定价引擎、分析报表维度、客户门户、采购、盘点、打印），目前全部按单一扁平 `categoryId` 语义。

**Schema 设计**（技术选型，我已决定）：用自引用树（`parentId` 自关联），不用"三个固定层级字段"的硬编码方案。理由：固定字段方案查询更简单，但"以后绝对不会要第 4 级"这个判断我没有把握；自引用树在应用层加校验限制当前最多 3 层，不改变数据结构就能后续放宽，技术风险更低。

```prisma
model ProductCategory {
  // ...现有字段不变...
  parentId String?
  parent   ProductCategory?  @relation("CategoryTree", fields: [parentId], references: [id])
  children ProductCategory[] @relation("CategoryTree")
}
```

- 迁移：加 `parentId` 列（nullable），存量记录全部保持 `parentId = null`（顶层），不自动归类。
- 层级深度校验放应用层（API 路由递归查 `parent` 链），不在 DB 层加 CHECK（Prisma 不支持表达式 CHECK）。
- `CategoryGroup`（采购品类分组）、`UomCategory`（计量单位分类）是不同概念，本次不碰。

**路由清单**：
- `app/api/product-categories/route.ts`：GET 支持返回树形结构，POST 支持传 `parentId`
- `app/api/product-categories/[id]/route.ts`：PUT 支持改 `parentId`（校验：不能选自己/子孙为父级、不能超 3 层）
- `app/[locale]/classic/operator/settings/page.tsx` 的 `ProductCategorySection`：平铺表格 → 树形列表（展开/折叠 + 选父级下拉）
- 其余 40+ 处 `categoryId` 筛选/下拉本次**不改**，继续按扁平列表（见风险点 1）

### 模块 B：移动端关键页面适配

**现状**（已用 Chrome DevTools 在 390×844 实测，截图在本机 scratchpad，可按需复制进 docs/preview/）：报价单列表、商品列表、订单列表三个"classic" Odoo 风格表格页，共享同一套公共表格/工具栏组件，**完全没有响应式处理**——顶部工具栏横向溢出、有个悬浮按钮错位、表格只能看到前 2-3 列，其余列（金额/状态/交期）被挤出屏幕。登录页不走这套组件，没有问题。三页表现一致，判定是组件级缺口。

**路由清单**：
- `app/[locale]/classic/**/layout.tsx` 里的顶部导航：加汉堡菜单（`<768px` 收起为抽屉）
- 公共表格/工具栏组件（报价单/订单/商品三页共用的那个）：加响应式断点

## 风险点

1. **40+ 处 `categoryId` 下拉/筛选不做树形化**：如果后续业务要求"按父分类筛选子分类下所有商品"，现在的 API 不支持，这是已知限制，不在本次范围内。
2. **移动端改法是交互行为变化，不是纯样式适配**：报价单/订单列表从表格切成卡片式（每条一张卡），配送中心的拖拽在触屏下本来就不可用，改成按钮操作——这些会改变操作手感，不只是改 CSS，需要你看过效果再定，不能只给文字描述。
3. **分类树建好之后，33 条存量分类仍然全部在顶层**——"树形结构能用"和"分类被整理成三级"是两件事，后者需要人工归类，本次不做（见下方判断点）。

1. **数据库备份**：已查明一直是全量 `pg_dump` 整库备份（无排表），下载入口 `/api/backups/[id]/download` 已存在，鉴权到 BOSS 角色（`system.backup.read`）。**不需要开发**。调研过程中额外查明生产库备份连续 29 天失败（2026-09-05→10-04，一张去重遗留审计表权限缺失导致 `pg_dump` 报错），已修复权限并验证新备份有效；该次临时授权你已决定不保留，已撤销（会导致自动备份再次失败，这几张一次性审计表建议直接清理或排除出 dump 范围，而不是授权绕过——需要你确认是否现在一起处理）。
2. **首页 quotation 数据加载**：已查明不是数据泄露。根因是 `lib/store.ts:188` 的 `hydrate()`，所有 `classic/*` 布局组件挂载时都会调用，无差别预拉 8 个接口（orders/waves/trips/invoices/customers/pricelists/stock-moves/purchases）写入 `localStorage`，与当前页面展示无关，是初版 mock-data 架构遗留的全局同步逻辑，不是专门为"首页要快"加的。鉴权受 middleware 路由表保护（`lib/rbac/route-map.ts:71-73`），行级隔离（`lib/orders-query.ts:198` `withRowScope`）对 SALES/EXTERNAL_SALES 按 `salesUserId` 收窄，口径与真实列表页一致，没有越权。这个预加载本身"合理但令人困惑"，且在 2vCPU 的生产服务器上是真实的性能浪费——是否要把它收窄成"只在用到的页面才拉对应数据"，算一项独立的性能优化，不在本次 4 项范围内，需要你确认是否要做。
