### 根因：客户截图 Pepper Green「走完销售流程库存回到原值」

- Place Order 页「确认」直接 `POST /api/orders` 建成 CONFIRMED。
- 扣库存只写在 `PUT` 的 PENDING→CONFIRMED 分支里，所以这条路径 **On Hand 从来没扣**。
- 中途下降的是 Forecast：旧算法对 WAVE_ASSIGNED / IN_DELIVERY 订单再减一次未送量；COMPLETED 后不再减，于是"涨回去"。
- 同一个"重复扣减"还出现在两处：
  - 波次缺货预警：库存 100，确认 60 后在手 40，却报「缺 20」；
  - 两套采购建议：已确认需求被减两次，导致建议偏大。

## 第四批（20261015）：销售出库时点改为与采购对称

客户反馈：「这两个数值还是有问题，在 sale 流程里有问题。在 purchase 流程里是正确的，可以参考。」

- 原因：20261014 版沿用了「订单确认即扣 On Hand」（计划 D2-①），和采购不对称。采购是确认只动 Forecast、收货才动 On Hand；销售却在确认时就把 On Hand 也扣了。
- 改为 Odoo 口径（计划阶段 6）：

  | 动作 | On Hand | Forecast |
  |---|---|---|
  | 销售确认 | 不变 | 减少 |
  | 货离仓（确认出发 / 完成） | 减少 | 不变 |
  | 已确认未出库就取消 | 不变 | 恢复 |

- 出库挂在所有货离仓的节点上：波次确认出发（含 22 点自动兜底）、手工建行程、行程完成、波次完成、批量开始配送、订单页改状态到配送中 / 完成。
- Forecast = 在手 + 采购在途 − 已确认待出库；可用 = 在手 − 待出库。低库存提醒改按「可用」判断。
- 兼容 20261014 那一天按旧口径确认的单：
  - 确认时已扣过的，出发时按「目标 − 已拿」不会重复扣；
  - 出发前被改行或撤回的，会先把库存还回去，出发时再扣。
- 账本核对的补扣项改为「配送中但从未出库扣库存的订单」。已确认待出库的单本来就不应有出库流水，不在此列。
- 本地验证（同一商品）：

  | 流程 | On Hand | Forecast |
  |---|---|---|
  | 起点 | 27 | 27 |
  | 采购确认 +10 | 27 | 37 |
  | 收货 | 37 | 37 |
  | 销售确认 5 | 37 | 32 |
  | 排入波次 | 37 | 32 |
  | 确认出发 | 32 | 32 |
  | 完成 | 32 | 32 |
  | 另一单确认 4 | 32 | 28 |
  | 取消该单 | 32 | 32 |

  另外验证了：跳过出发直接完成会在进入配送中时扣；旧口径已扣的单出发不重复扣；商品列表页显示一致；账本核对 0 差异。
- 测试：全量测试 985 条，失败 7 条，均为既有基线问题；`npm run build` exit 0。

## 第六批（20261020）：调度台「标记完成」链路修复

客户：「订单号 D-261018-xxx，我在调度台点的标记完成，然后修复全部问题」。沙箱连不上生产库，按真实路径在本地走了一遍：每日生成波次 → 调度台分配 → 分配完成 → 确认出发（手动 / 22 点自动）→ 标记完成。找到并修复：

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | 波次「标记完成」只写波次完成时间，出发时生成的司机行程一直是 PENDING | 司机端还挂着这一趟；司机提成不结；工作台退货统计漏掉 | 标记完成时把该波次的行程一并置为 COMPLETED，并结司机提成 |
| 2 | 草稿发票编号取「按字符串排序最大的 INV- + 1」，两套编号并存（自动 5 位 / 发票页 INV-总数+1）就会算错、撞唯一约束；错误被吞掉 | 订单完成了却**没有发票**，没有任何提示 | 改为按数字取最大号（与 VB/PO 等单据同一套 `nextSequenceName`），撞号自动重取最多 3 次；发票页手动开票的 INV-数字 号也改由服务端发 |
| 3 | 自动草稿发票账期写死 monthly、到期日为空 | 逾期检测对这些发票永远查不到 | 账期取客户档案，按账期算到期日（与手动开票同口径） |
| 4 | 标记完成只给「已确认 / 已排波次」的单出库，「配送中」的单默认出发时已扣；出发那步出库在事务提交后单独跑，失败了订单照样是配送中 | 这种单完成后 On Hand 永远不扣 | 完成时对所有本次完成的单按「目标 − 已拿」幂等补扣（扣过的不会重复）；出发时逐单出库互不影响 |
| 5 | 完成时对整批订单无条件把实送量覆盖成下单量 | 早已完成、差异处理改过实送量的单被覆盖 | 只回填本次从在途变为完成的单 |

## 第七批（20261020）：采购收货超出订购数量

- **原因**：采购退货扣批次用的是 FEFO，范围是这个商品的**全部**批次（保质期早、到货早的先扣），所以先扣到了别的采购单收进来的老批次 LOT-01105。结果是老批次被凭空扣掉，本单的 LOT-01106 反而留着实际早已退回的余量。商品总在手量是对的，错的是扣在了哪个批次上。#46 修的是退货数量和金额，没改扣批次的顺序；作废 PO-00224 的那次数据迁移是按本单批次扣的，但它之前那笔 450 箱退货仍然挂在老批次上。
- **修复**：
  - 采购退货先扣**这一行收货收进来的批次**（依据收货流水上的采购行 + 批次；多次收货时，最近一次收的先扣）；
  - 只有本单批次余量不够（这批货已被卖掉一部分）时，差额才按 FEFO 扣别的批次。
  - 其他出库（销售、报废、盘点）不受影响，照旧 FEFO。
- 本地验证（Carrot，另一张 PO 先收 100 → 测试 PO 订 50 误收 500 → 退 450）：
  - 旧代码：450 里有 376 扣在了别的批次上（两个旧批次被扣空），本单批次只扣了 74；
  - 新代码：450 全部从本单批次扣（500 → 50），其他批次不动；
  - 本单批次只剩 20 时再退 50：先扣光本单的 20，差额 30 才按 FEFO 扣别的批次。
- 测试：新增 `tests/purchase-return-own-lots.test.ts`（4 条）；全量 986 条，失败 8 条，与 main 相同；`npm run build` exit 0。
- **生产上 PO-00224 已发生的错挂未在本批修正**：那笔 450 箱退货的批次分配需要一次数据改挂（把挂在 LOT-01105 等别的批次上的退货流水改挂回 LOT-01106；数量、金额、凭证都不变）。客户确认后见第十七批。
