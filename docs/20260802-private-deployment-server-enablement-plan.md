## 2. 五个必须先解决的阻塞项

### B1（最紧急，且有时间窗）服务器在伦敦，客户在爱尔兰 — 数据跨境

服务器位于 **DO lon1（英国）**。客户是爱尔兰实体（发票模板 `pic/发票的 PDF 格式Sales-Order-D120827.pdf` 上 VAT 号为 `IE...`）。EU → UK 属于 GDPR 意义上的跨境传输，需要合规依据。合同第十二条明确要求「安全性与合规」。

**为什么这条排第一：现在这台机器是空的，换区域是零成本的。** 一旦 Odoo 历史数据和生产库落上去，再迁就是一次完整的停机搬迁。

- 若客户/其法务不接受数据出境 → 现在重建到 `ams3`(阿姆斯特丹) 或 `fra1`(法兰克福)，代价仅为重新执行本计划的阶段 2
- 若接受 → 书面确认后按现状推进

⛔ 建议在拿到客户明确答复前，**不要开始阶段 3 及之后的任何步骤**。

### B2 内存不足以安全承载两套系统，且没有 swap

需要同机常驻的进程：

| 进程 | 稳态内存估算 |
|---|---|
| 操作系统 + fail2ban + 自动更新 | ~450 MB（实测当前占用） |
| 新系统 Next.js（standalone） | 350–500 MB |
| 新系统 PostgreSQL | 300–500 MB |
| Odoo 12（2 workers） | 600 MB–1.2 GB |
| Odoo PostgreSQL | 300–500 MB |
| Nginx 反向代理 | 30–50 MB |
| **稳态合计** | **约 2.0–3.2 GB** |
| Chromium 渲染 PDF 时的瞬时叠加 | **+300–500 MB** |

峰值可达 3.5–3.7 GB，逼近 3.8 GB 物理上限，而**当前 Swap 为 0**。Linux 在无 swap 时触发 OOM killer 会直接杀掉内存占用最大的进程 —— 通常就是 Odoo 或某个 PostgreSQL。

这会**直接违反合同条款**「任一系统的升级、重启、故障或数据操作，不得未经授权影响另一套系统的正常运行及数据安全」：新系统打一批 PDF 就可能把 Odoo 打死。

处理：
1. **立即加 4 GB swap 文件**（零成本，5 分钟）。这是兜底，不是解决方案 —— PostgreSQL 跑在 swap 上性能会明显下降。
2. **建议客户升配到 4 vCPU / 8 GB**。合同第三条写明服务器费用由甲方承担，因此这是甲方的成本决策，我方需要给出的是依据（即上表）。DO 同规格线升配可在线完成，仅需一次重启。
3. 若客户坚持不升配：必须在验收文档里书面记录「2 vCPU/3.8 GB 为客户选定规格，双系统并发高峰下的资源争抢风险已告知」，并把 Odoo workers 压到 1、PostgreSQL `shared_buffers` 调低，用性能换稳定。

### B3 Odoo 12 无法原生安装在 Ubuntu 26.04

Odoo 12（2018 年发布）要求 **Python 3.5–3.7**，Ubuntu 26.04 自带 **Python 3.14**。`apt install` 或源码部署都跑不起来，这是硬不兼容，不是配置问题。

**解法：Odoo 12 全部走 Docker**，用官方 `odoo:12.0` 镜像（Debian 基底，自带兼容的 Python）+ `postgres:12` 镜像。

这个解法有个附带好处：合同要求的「程序运行环境相互独立」「系统账号及权限相互独立」由容器边界天然满足，不需要额外设计。

⚠️ **前置风险**：如果客户现网的 Odoo 12 装了定制模块或第三方模块，官方镜像不含这些模块，需要把 `addons` 目录一并搬迁并逐个验证依赖。这是 Odoo 迁移最常翻车的地方，必须在阶段 0 摸清楚。

### B4 服务器上目前没有 Odoo，现网 Odoo 在别处

实测 `/opt/odoo`、`/etc/odoo`、`/var/lib/odoo`、`/var/lib/postgresql` 均不存在。也就是说客户现在跑的 Odoo 12 在另一台机器上，本次要做的不只是「装一个 Odoo」，而是**把现网 Odoo 12 连同历史数据整体搬迁到这台服务器**。

合同第十一条要求「原 Odoo 12 历史数据须保持完整、可查询」，所以这是一次带数据的迁移，不是全新安装。需要客户提供现网 Odoo 的访问权限。

### B5 代码层三处硬耦合，其中一处正好是备份

上游文档第 2.2/2.3 节已识别两处，实际复查后是**三处**：

| 文件 | 耦合 | 影响 |
|---|---|---|
| `lib/db.ts` | 写死 `PrismaNeon` + `@neondatabase/serverless`（WebSocket 协议） | 连不上客户服务器上的标准 PostgreSQL，**私有化的第一道门** |
| `app/api/upload-image/route.ts` | 硬编码 `@google-cloud/storage` | 客户服务器无 GCS |
| `app/api/purchase-orders/pdf-extract/route.ts` | 同上 | 同上 |
| **`lib/backup.ts`** | **同上** | **备份是合同硬要求，私有化下备份产物不能落在 GCS** |

`lib/backup.ts` 这条是上游文档漏掉的 —— 8 月 1 日刚合并的备份功能整套建立在 GCS 上，私有化场景需要重写存储落点。

## 3. 目标架构

```
                    Internet
                       │
              ┌────────┴────────┐
              │  Nginx (80/443) │  Let's Encrypt 自动续期
              │  反向代理+分流   │
              └───┬─────────┬───┘
      new.<域名>  │         │  odoo.<域名>
                  ▼         ▼
        ┌──────────────┐  ┌──────────────┐
        │ veggie-app   │  │ odoo12       │   ← 独立容器
        │ Next.js:3000 │  │ Odoo:8069    │
        │ user: veggie │  │ user: odoo   │   ← 独立系统用户
        └──────┬───────┘  └──────┬───────┘
               │                 │
        ┌──────▼───────┐  ┌──────▼───────┐
        │ postgres:17  │  │ postgres:12  │   ← 两个独立实例
        │ :5433        │  │ :5432        │      独立账号、独立数据卷
        └──────────────┘  └──────────────┘

  /data/veggie/{uploads,backups,pgdata}     ← 独立文件目录
  /data/odoo/{filestore,backups,pgdata}        权限隔离，互不可读
```

**端口 / 目录 / 账号规划（对应合同「六个相互独立」逐条）**

| 合同要求 | 落地方式 |
|---|---|
| 程序运行环境独立 | 两组独立 docker compose 项目，不共享网络、不共享卷 |
| 数据库独立 | 两个 PostgreSQL 容器实例（PG17 / PG12），独立端口、独立超级用户、独立数据卷 |
| 文件存储目录独立 | `/data/veggie/*` vs `/data/odoo/*`，属主分别为 `veggie`/`odoo`，`chmod 750` 互不可读 |
| 系统账号权限独立 | 新建 Linux 用户 `veggie`、`odoo`，各自 rootless 或受限 docker 权限，互不能操作对方容器 |
| 访问地址端口独立 | 内部 3000 / 8069 只监听 127.0.0.1，对外统一经 Nginx 按子域名分流 |
| 日志备份机制独立 | 各自的 journald unit、各自的 logrotate、各自的备份 cron 与备份目录 |

## 4. 分阶段执行计划

### 阶段 0：决策与摸底（阻塞后续，不占开发工时）

| # | 事项 | 负责 | 产出 |
|---|---|---|---|
| 0.1 | 数据居留决策：接受伦敦 / 迁 EU 区（B1） | 客户 + 法务 | 书面确认 |
| 0.2 | 服务器规格决策：维持 3.8 GB / 升 8 GB（B2） | 客户 | 书面确认 |
| 0.3 | 现网 Odoo 12 摸底：版本号、装了哪些 addons、DB 大小、filestore 大小、PG 版本 | 我方（需客户给访问权限） | 摸底报告 |
| 0.4 | 域名与 DNS：确认 `new.*` / `odoo.*` 子域名，A 记录指向本机 | 客户 | DNS 生效 |
| 0.5 | 异地备份目的地：客户另一台机器 / S3 兼容对象存储 / 其他（合同要求「至少一份保存在不同于主服务器的位置」） | 客户 | 确认 + 凭据 |

> 0.1 和 0.2 未确认前不要进入阶段 2 之后。0.3 未完成不要承诺 Odoo 迁移工期 —— 定制模块的数量直接决定这一段是 1 天还是 1 周。

### 阶段 1：代码解耦（可与阶段 0 完全并行，不碰客户服务器）

| # | 任务 | 说明 | 规模 |
|---|---|---|---|
| 1.1 | `lib/db.ts` 双驱动 | 按 `DATABASE_DRIVER=neon\|pg` 切换，私有化用 `@prisma/adapter-pg`。Prisma schema 不动 | 小 |
| 1.2 | 抽 `lib/storage.ts` | `StorageProvider` 接口 + `GcsProvider` + `LocalDiskProvider`，按 `STORAGE_DRIVER` 切换 | 中 |
| 1.3 | 改造 3 个 GCS 调用点 | upload-image / pdf-extract / **backup.ts** 全部改走 `lib/storage.ts` | 中 |
| 1.4 | 备份脚本脱云 | `pg_dump` + `tar` 落本地目录 + rsync 异地，替代现有 GCS 签名 URL 方案 | 中 |
| 1.5 | 本机端到端验证 | 用 docker compose 在**自己机器上**起「标准 PG + 本地磁盘存储」跑通全链路 | 中 |

⛔ **1.5 是硬性关卡**：不要把客户服务器当试错环境。所有驱动切换问题必须在本地暴露完。

### 阶段 2：服务器基线加固（阶段 0.1/0.2 确认后执行）

1. 加 4 GB swap（`/swapfile`，`vm.swappiness=10`）
2. 时区设为客户所在时区（当前 UTC，需按爱尔兰业务确认是否改 `Europe/Dublin`）
3. 安装 Docker Engine + compose plugin
4. 创建系统用户 `veggie` / `odoo`，建立 `/data/{veggie,odoo}` 目录树与权限
5. 安装 Nginx + certbot，签发两个子域名证书，配置自动续期
6. ufw 复核：仅保留 2200/80/443，容器端口一律绑 `127.0.0.1`
7. 基础监控：磁盘/内存告警（内存是 B2 的风险点，必须有告警而不是等 OOM）
8. 产出《服务器基线配置记录》

### 阶段 3：Odoo 12 迁移上机

1. 现网导出：`pg_dump` + filestore 打包（需停业务窗口或用一致性快照）
2. 起 `postgres:12` + `odoo:12.0` 容器，挂 `/data/odoo/*`
3. 恢复数据库 + filestore，逐个装回定制 addons
4. 功能抽验：登录、历史订单查询、报表打印、附件可见
5. 合同要求「历史数据完整可查询」→ 需与客户约定一份抽验清单并共同签字

### 阶段 4：新系统上机

1. 镜像构建仍走 GitHub Actions（**不在这台 2 vCPU 机器上 `npm run build`**，内存不够且会拖垮 Odoo），推送到镜像仓库
2. 服务器拉取镜像 + `docker compose up`
3. 起 `postgres:17`，`prisma migrate deploy` 建表
4. 数据迁移：现有 Neon 生产库 → 本地 PG（`pg_dump`/`pg_restore`）
5. 全链路验收：合同第四条的「客户下单 → 仓库分拣 → 司机电子签收 → 生成导出数据」闭环
6. 两系统并行观察：连续跑一周，监控内存峰值，验证 B2 的估算

### 阶段 5：备份与恢复（合同硬要求，四条逐条落地）

| 合同条款 | 落地 |
|---|---|
| 数据库定期自动备份 | 两套各自的 cron `pg_dump`（每日全量），保留策略 7 日 + 4 周 + 6 月 |
| 程序文件及上传文件定期备份 | 两套各自 `tar` 打包 `/data/*/uploads`、`/data/odoo/filestore` |
| 至少一份保存在不同位置 | rsync/rclone 同步到阶段 0.5 确认的目的地 |
| 备份可正常恢复 | **必须做一次真实恢复演练**：在临时容器里恢复出可登录的实例并出具报告 |
| 甲方可取得完整备份文件 | 交付备份目录访问方式 + 《备份与恢复操作手册》 |

⛔ 「有备份文件」不等于「备份可恢复」。恢复演练要写进验收清单，这是最容易在验收时被跳过、出事时最致命的一环。

### 阶段 6：交接（合同「账号与资料掌握」条款）

- 《系统交接清单》：服务器 root/sudo、两套数据库超级用户、两套系统管理员、备份路径与凭据、部署脚本、镜像仓库、源码仓库权限
- **账号必须由甲方自己创建或当场改密**，不是我方建好再"共享"给甲方 —— 合同要求「乙方不得以任何方式限制甲方访问、导出、备份或接管」
- 《服务器部署与隔离操作手册》《备份与恢复操作手册》《双系统运维日常检查表》
- 保修期响应机制书面化（合同第十三条：6 个月免费保修，24 小时响应）

## 5. 关键风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **内存不足触发 OOM，一套系统拖死另一套** | 直接违约 | 加 swap（兜底）+ 力劝升配（根治）+ 内存告警 |
| **数据居留合规**（lon1 在英国，客户在爱尔兰） | 合规风险，且越晚改成本越高 | 阶段 0.1 书面决策，现在改零成本 |
| **Odoo 12 定制模块搬不动** | 阶段 3 工期不可控 | 阶段 0.3 先摸清 addons 清单再报工期 |
| Odoo 12 已停止官方支持（2018 版） | 安全补丁缺失 | 只对内网/受限来源开放，Nginx 层加访问控制；合同已定位其为「过渡与历史查询系统」 |
| 迁移窗口业务中断 | 客户业务受影响 | 阶段 3/4 的数据导入安排在非营业时段，先做一次演练迁移 |
| 单机单点 | 服务器挂了两套系统全停 | 合同未要求高可用；但备份异地存放 + 恢复手册必须到位，作为最低限度的业务连续性保障 |

## 6. 需要客户回答的问题（按紧急度）

1. **【最紧急】数据可以放在英国（伦敦）吗？** 还是必须留在欧盟境内？现在服务器是空的，改区域零成本。
2. **服务器要不要升到 4 vCPU / 8 GB？** 依据见 §2 B2 的内存测算。费用按合同由甲方承担。
3. **现网 Odoo 12 在哪台机器上？能否提供访问权限做摸底？** 装了哪些定制/第三方模块？
4. **异地备份放哪？** 客户自有的另一台机器，还是可以用对象存储？
5. **域名怎么分？** 建议 `new.<域名>` / `odoo.<域名>`，需要客户在 DNS 上加 A 记录。
6. **可接受的迁移停机窗口是什么时候？**（Odoo 数据导出需要一致性快照）
